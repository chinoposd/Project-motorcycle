01  บทนำและหลักการจัดทำ

1.1 วัตถุประสงค์ของเอกสาร

• บันทึกข้อกำหนดที่ผู้พัฒนาได้ตัดสินใจแล้ว เพื่อใช้เป็นฐานสำหรับออกแบบวงจร ฐานข้อมูล APIs และส่วนติดต่อผู้ใช้
• แยกข้อกำหนดที่ยืนยันแล้วออกจากสมมติฐานและค่าที่ต้องกำหนดหลัง Pilot หรือการตรวจสอบอุปกรณ์จริง
• เป็นเกณฑ์อ้างอิงสำหรับออกแบบการทดสอบ Traceability และบริหารการเปลี่ยนแปลงระบบ

เบื้องต้น | ตัวเลือกชั่วคราว เปลี่ยนได้หลังมีผลทดลอง เช่น รุ่นกล้อง

02  ขอบเขตงานและข้อยกเว้น

2.1 งานที่จะพัฒนา

• เว็บ Responsive สำหรับสมัครสมาชิก ตรวจสิทธิ์ ขอเริ่มรอบ และดูประวัติตามบทบาท
• Supabase Auth, PostgreSQL,Row Level Security (การกำหนดสิทธิ์เข้าถึงข้อมูล ) , Realtime, Edge Functions สำหรับบัญชี สิทธิ์ คำสั่งและประวัติรถ
• ระบบ NFC ผ่าน PN532 สำหรับยืนยัน UID แบบออนไลน์ทุกครั้ง
• ระบบ ESP32-S3 อ่าน ATGM336H GNSS และ Battery Management System(ระบบจัดการแบตเตอรี่ ) , เก็บข้อมูลออฟไลน์, เล่นเสียงแจ้งเตือน และตรวจความพร้อมก่อนเริ่มรอบ
• ระบบ Raspberry Pi 5 4GB ประมวลผล YOLO Segmentation ร่วมกับกล้องและ MPU6050 และเป็นประตูสื่อสาร 4G LTE
• ระบบ Geofencing (รั้วเสมือนจริง) ใช้ Main Polygon หลักหนึ่งชุดสำหรับควบคุมสิทธิ์ Student/Employee; เมื่อออกนอกเขตให้บันทึกและแจ้งเตือนเท่านั้น ไม่จำกัดแรงบิด กำลัง หรือความเร็วระหว่างขับ ตาม C-112–C-115
• เครื่องมือสำหรับ Admin/Manager ในการเฝ้าระวัง แก้ไขปัญหา ปรับตั้งค่าที่ได้รับอนุญาต และตรวจสอบ Audit Log(บันทึกการตรวจสอบ)
2.2 สิ่งที่ไม่รวมในโครงการหรือถูกข้าม

• ไม่พัฒนาระบบขับขี่อัตโนมัติ เลี้ยวอัตโนมัติ เบรกอัตโนมัติ หรือควบคุมมอเตอร์ด้วยผล AI
• ไม่เพิ่มฟังก์ชันเตือนความเร็วเกินหรือจำกัดความเร็วทั่วไป และไม่เพิ่มการลดแรงบิด/กำลังมอเตอร์จาก Geofencing (รั้วเสมือนจริง) ระหว่างขับ; ให้ใช้การแจ้งเตือนและเงื่อนไขห้ามเริ่ม Session ใหม่ตามข้อกำหนดล่าสุด
• ไม่พัฒนาระบบชำระเงิน ค่าโดยสาร ตารางเดินรถ ระบบจองรถล่วงหน้าหรือการจัดการรถหลายคัน; การสงวนสิทธิ์ 5 นาทีเป็นกลไกป้องกันการชนกันของคำขอ ไม่ใช่บริการจองล่วงหน้า
• ไม่เพิ่ม LED หรือหน้าจอแจ้งเตือนใหม่บนตัวรถ และไม่บังคับ Multi-Factor Authentication (การยืนยันตัวตนด้วยหลักฐาน )ของบัญชีเว็บ
• ไม่เพิ่มระบบสำรองข้อมูล/กู้คืน Supabase เป็นงานพัฒนา และยังไม่กำหนดระบบส่งออก PDF/CSV
• ไม่เพิ่มระบบปิด Raspberry Pi อัตโนมัติ และไม่เพิ่มฟังก์ชันจัดการความร้อนอัตโนมัติในขั้นนี้
• ไม่เปิดให้บริการเชิงพาณิชย์หรือทดลองบนถนนสาธารณะนอกพื้นที่ที่ได้รับอนุญาต
[ตารางจากเอกสาร Word]
ข้อควรระวัง แม้ไม่พัฒนาระบบสำรองข้อมูล Supabase ความเสี่ยงด้านข้อมูลสูญหายยังมีอยู่ และแม้จะข้ามการกำหนดเกณฑ์บางข้อทางด้านความปลอดภัย ก็ไม่ใช่การยกเว้นเงื่อนไขว่าต้องพิสูจน์ความปลอดภัยก่อนทดลองขับจริง
[/ตาราง]

03  สถาปัตยกรรมระบบและเส้นทางข้อมูล

3.1 ภาพรวมเชิงตรรกะ

[ตารางจากเอกสาร Word]
ชั้นระบบ | องค์ประกอบ | หน้าที่ / ข้อจำกัด
Client | Responsive Web | สมัครสมาชิก เข้าสู่ระบบ จัดการบัญชี ขอเริ่มรอบ ดูสถานะ/ประวัติ; ไม่มีสิทธิ์ส่งคำสั่งมอเตอร์โดยตรง
Cloud | Supabase Auth + PostgreSQL/RLS + Edge Functions + Realtime | เซิร์ฟเวอร์เป็นผู้ตัดสินสิทธิ์และ Session แบบ Atomic; จัดเก็บข้อมูลและ Audit
Gateway / AI | Raspberry Pi 5 RAM 4GB + LTE/4G + YOLO + กล้อง + MPU6050 | เครือข่ายเพียงทางเดียวของรถ ประมวลผลภาพและ Inertial Measurement Unit (เซนเซอร์วัดการเคลื่อนไหว ) ส่งสถานะ AI ผ่าน UART
Edge Control | ESP32-S3 + GNSS + PN532 + BMS + local storage + audio | ตรวจเงื่อนไขเริ่มรอบ พิจารณาคำอนุมัติ ลงบันทึกข้อมูล ขับเสียงและ Geofencing(รั้วเสมือนจริง)
Vehicle native | VOTOL EM100 / QS motor / BMS / Keyless Motor Ready | ระบบไม่ใช้กุญแจรถจริง; ต้องพิสูจน์วงจรอนุญาต Motor Ready และระบบความปลอดภัยเดิมก่อนทดลองขับ
[/ตาราง]

3.2 ทิศทางการสื่อสาร

Web ↔ Supabase (Auth, Edge Functions, Realtime) ↔ เครือข่าย 4G LTE บน Raspberry Pi ↔ UART สองทิศทาง ↔ ESP32-S3 ↔ GPS / NFC / BMS / เสียง / วงจรอนุญาตเริ่มมอเตอร์ที่พิสูจน์แล้ว
กล้อง → Raspberry Pi YOLO Segmentation; MPU6050 → Raspberry Pi I²C; ผลวิเคราะห์และสถานะ AI → UART → ESP32 → เสียงภาษาไทยและบันทึกเหตุการณ์
[ตารางจากเอกสาร Word]
ขอบเขตความเชื่อถือ Raspberry Pi ส่งต่อคำอนุมัติ แต่ไม่ใช่ผู้ตัดสินสิทธิ์ขั้นสุดท้าย; ESP32 ต้องตรวจลายมือชื่อดิจิทัล Nonce และ Command ID จากเซิร์ฟเวอร์ก่อนยอมรับ Session Start
[/ตาราง]

3.3 กลไกเส้นทางคำสั่งแบบออนไลน์

• ผู้ใช้ยืนยัน NFC หรือกดเริ่มผ่านเว็บ → Supabase ตรวจ Account Approved, Driving Permission และข้อจำกัดบทบาท; ก่อน Session Start ต้องมีหลักฐานการยืนยันตรวจสภาพรถของรอบนั้น (C-129/C-130/C-136)
• เซิร์ฟเวอร์สงวนสิทธิ์แบบ Atomic สูงสุด 5 นาทีสำหรับรถหนึ่งคัน
• Raspberry Pi รับการเปลี่ยนแปลงผ่าน Realtime และดึงคำอนุมัติผ่าน Edge Function เพื่อตรวจสอบความถูกต้องและอายุ
• ESP32 ทำ Challenge–Response ตรวจลายมือชื่อและเงื่อนไขความปลอดภัยทั้งหมด; เซิร์ฟเวอร์ออก Start Authorization สำหรับอนุญาตเปิด Motor Ready เมื่อเงื่อนไขครบ โดยการอนุมัติคำสั่งยังไม่ใช่ผลยืนยันว่าเริ่มรถสำเร็จ
• หลังได้รับ Start Authorization ให้ ESP32 ใช้วงจรอนุญาตแรงดันต่ำที่พิสูจน์แล้ว และตรวจยืนยันว่า Motor Ready เกิดขึ้นจริงด้วยวิธีที่เชื่อถือได้จากตัวรถ จากนั้นส่ง Start Confirmation ที่สัมพันธ์กับ Session ID และ Command ID; เซิร์ฟเวอร์จึงเปลี่ยน Pending Start เป็น Active Session หลังได้รับผลยืนยันจริงเท่านั้น ไม่ใช้เพียง ACK หรือการตรวจเงื่อนไขผ่านเป็นหลักฐาน

4.1 ข้อกำหนดงานไฟฟ้า

• ใช้ DC-DC หนึ่งชุด แต่แยกฟิวส์/การป้องกันสำหรับ Raspberry Pi, โมดูล 4G, ESP32-S3 และระบบเสียงตามความเหมาะสม
• เลือกอุปกรณ์จากแรงดันแบตเตอรี่จริง กระแสต่อเนื่องและกระแสกระชากสูงสุด และการทดสอบสภาวะไฟตก/ไฟกระชาก
• ตรวจระดับลอจิก UART การต่อกราวด์ การแยกสัญญาณจากภาคกำลัง และมาตรการ  Electromagnetic  Interference (การรบกวนทางแม่เหล็กไฟฟ้า ) ก่อนเชื่อมต่อกับรถ
• อุปกรณ์ Pi และ ESP32 ได้รับไฟตลอดที่แบตเตอรี่ยังจ่ายได้ แม้ปิดสวิตการทำงานของรถ เมื่อจอด Pi ยังคงเปิด แต่หยุด YOLO และลดงานที่ไม่จำเป็น
• ความผิดพลาดของอุปกรณ์เสริมหรือ DC-DC ต้องไม่เป็นเหตุจากวงจรเสริมให้มอเตอร์ถูกตัดกำลังกะทันหัน
4.2 สถานะจุดเชื่อมต่อมอเตอร์

ยังไม่ระบุขาและระดับแรงดัน E-lock/Enable แบบตายตัว ต้องตรวจสอบเอกสาร VOTOL EM100 และวงจรจริง เลือกจุดควบคุมแรงดันต่ำที่สามารถอนุญาตให้เริ่มหลัง Session Start และไม่ข้ามวงจรความปลอดภัยของรถและ BMS หากยังพิสูจน์ความปลอดภัยไม่ได้ ให้หยุดการทดสอบขับจริงและทำเฉพาะการทดสอบความปลอดภัย

5.1 การสมัครและอนุมัติ

• ใช้ Supabase Auth ยืนยันอีเมลและรหัสผ่าน; ทุกบัญชีใหม่ Pending จนกว่า Admin อนุมัติ
• สมัครด้วยชื่อ–นามสกุล เบอร์โทรศัพท์ อีเมล และประเภทผู้ใช้ที่สมัคร โดยไม่บังคับรหัสนักศึกษา/บุคลากร
• Admin ตรวจสอบข้อมูลตามความเหมาะสมก่อนอนุมัติ การกรอกชื่อและเบอร์โทรเพียงอย่างเดียวไม่พิสูจน์สถานภาพของผู้สมัคร
• สถานะ: Pending, Approved, Rejected, Suspended; ผู้ใช้ห้ามแก้บทบาทของตัวเอง
• ไม่ใช้ MFA สำหรับบัญชีทุกประเภท; รีเซ็ตรหัสผ่านผ่านลิงก์อีเมลของ Supabase Auth เท่านั้น
5.2 กติกาเวลา

Student (นักศึกษา) และ Employee (บุคลากร) เริ่ม Session ใหม่ได้เฉพาะวันและช่วงเวลาที่ Admin (ผู้ดูแลระบบ) กำหนดและเปลี่ยนได้ตลอดเวลาผ่านเว็บไซต์ โดยไม่มีค่าเวลาเริ่มต้นตายตัวจากมตินี้ และตรวจสิทธิ์ตามเวลาเซิร์ฟเวอร์ก่อนเริ่มจริง; หากเริ่มถูกต้องแล้วให้ขับต่อจนจบรอบแม้เลยเวลาที่กำหนด โดยไม่ตัดกำลังมอเตอร์; Manager ยกเว้นข้อจำกัดวันและเวลา ส่วน Admin ไม่ใช่บัญชีผู้ขับ
5.3 การระงับสิทธิ์

หาก Admin ระงับบัญชีหรือบัตรระหว่างมีสิทธิ์จอง 5 นาที เซิร์ฟเวอร์ตรวจซ้ำก่อน Session Start และยกเลิกคำขอทันทีที่ไม่ผ่านสิทธิ์ แต่ไม่ตัดกำลังรถที่มี Active Session อยู่แล้ว
06  NFC และการลงทะเบียนบัตร

• ตรวจสิทธิ์ UID แบบออนไลน์ทุกครั้ง; ไม่อนุญาตเริ่มรอบ NFC เมื่อ Supabase ติดต่อไม่ได้
• Admin ลงทะเบียนบัตรจริงผ่านเว็บโดยเปิด Enrollment Mode เลือกบัญชีที่ Approved แล้วนำบัตรแตะ PN532 บนรถ
• ESP32 ส่ง UID ผ่าน UART→Pi→Edge Functions และตรวจ UID ไม่ซ้ำกับบัญชีอื่น; หนึ่งบัญชีมีบัตรที่ใช้งานได้เพียงหนึ่งใบ
• โหมดลงทะเบียนต้องมี Time to live(ระยะเวลาที่ข้อมูลหมดอายุ) และเข้าไม่ได้ระหว่างมีรอบขับขี่; บันทึก Audit Log(บันทึกการตรวจสอบ)
• หากบัตรหาย Admin เพิกถอน UID เดิมและลงทะเบียนบัตรใหม่ โดยไม่ตัดการใช้งานที่กำลังขับ
• ใช้ UID-only ตามขอบเขตที่ตกลง แต่ต้องระบุความเสี่ยงบัตรถูกคัดลอกไว้ในรายงาน
[ตารางจากเอกสาร Word]
ข้อจำกัดด้านความปลอดภัย UID ของ NFC บางชนิดสามารถทำสำเนาได้ จึงไม่ควรเขียนว่าโซลูชันนี้ป้องกันการปลอมบัตรได้สมบูรณ์; มาตรการจริงคือสิทธิ์ออนไลน์ การล็อก Session และการเพิกถอน UID

7.2 ขั้นตอนเริ่มรอบ

• ยืนยันสิทธิ์ผ่าน NFC หรือ Responsive Web App; ระบบไร้กุญแจไม่บังคับสวิตช์ OFF→ON หรือให้กดยืนยันที่รถเพิ่ม แต่ต้องพิสูจน์ว่าผู้ใช้อยู่ใกล้รถก่อน Motor Ready (C-136–C-139)
• Supabase ตรวจ Account Approved, Driving Permission, role, เวลาที่อนุญาต, เงื่อนไข BMS, การชาร์จ, ความพร้อม AI สำหรับนักศึกษาและบุคลากร, Polygon ที่ตั้งไว้ และสถานะรถ; หากขาด Driving Permission ห้ามอนุมัติการเริ่มใช้งาน
• อนุมัติการใช้งานรอบ แบบ atomic สูงสุด 5 นาที; คำขอจากผู้ใช้อื่นถูกปฏิเสธจนหมดสิทธิ์/ยกเลิก/เริ่มจริง
• ก่อน Session Start ทุกครั้ง ผู้ขับที่มี Account Approved ต้องได้รับ Driving Permission ที่ Admin เปิดหลังทีมงานยืนยันการแนะนำ (C-136); ผู้ขับตรวจสภาพรถเบื้องต้น เช่น เบรก/ยาง และยืนยันผ่าน Responsive Web App แม้ขอเริ่มผ่าน NFC พร้อมบันทึกตัวตนและเวลาที่ยืนยัน (C-129/C-130); หากไม่มีหลักฐานยืนยันของรอบนั้น ห้ามเริ่มรถ
• ก่อนเริ่มจริง ESP32 ตรวจว่ารถหยุดนิ่ง คันเร่งศูนย์ BMS ปกติ สถานะระบบไร้กุญแจปลอดภัย และเงื่อนไข AI ตามบทบาท; ถ้าตรวจความหยุดนิ่งหรือคันเร่งไม่ได้อย่างเชื่อถือได้ ห้ามเริ่มรอบใหม่
• ESP32 สร้าง Nonce ใหม่และขอคำอนุมัติที่ลงลายมือชื่อ; ตรวจ Public Key, User ID, Vehicle ID, Session ID, Command ID, Nonce และความใหม่ของคำสั่ง
• เซิร์ฟเวอร์อนุมัติ Start Authorization ก่อนเปิด Motor Ready เมื่อ ESP32 ตรวจเงื่อนไขครบ; ESP32 ใช้วงจรแรงดันต่ำที่ผ่านการทดสอบ แล้วตรวจยืนยัน Motor Ready จริงและส่ง Start Confirmation ที่ผูกกับ Session ID/Command ID; เซิร์ฟเวอร์จึงบันทึก Active Session หลังได้รับผลยืนยันนี้ โดยไม่รอให้รถเคลื่อนที่แล้วจึงนับเวลา Session
• หากสื่อสารขัดข้องหรือยืนยัน Motor Ready/Start Confirmation ไม่ได้ ให้กันการเริ่ม Session ใหม่และประสานสถานะรถกับเซิร์ฟเวอร์ก่อน; ไม่ถือ ACK ว่าเป็นหลักฐาน Motor Ready และห้ามสั่งตัดกำลังขณะรถกำลังเคลื่อนที่เพียงเพื่อแก้สถานะฐานข้อมูล
7.3 แข่งกันขอสิทธิ์ / คำสั่งซ้ำ

เซิร์ฟเวอร์ต้องรักษาข้อจำกัดรถหนึ่งคันหนึ่ง Reservation/Active Session ภายในธุรกรรมเดียว การส่งคำสั่งซ้ำต้องใช้ Command ID เดิมจนหมด Time to Live(ระยะเวลาที่ข้อมูลหมดอายุ) และ ESP32 ต้องประมวลผลแบบ Idempotent หากคำสั่งหมดอายุหรือไม่ตรงเจ้าของสิทธิ์ต้องปฏิเสธ
7.4 การจบรอบ

• เมื่อมีคำขอจบจากเจ้าของ Session ผ่าน NFC/เว็บไซต์ ต้องยืนยันรถหยุดนิ่งอย่างเชื่อถือได้ และตรวจ Return Zone หรือข้อยกเว้นที่มติ C-027/C-028 อนุญาต ก่อนพิจารณาปิด Motor Ready; ต้องมีผลยืนยัน Motor Ready ปิดจริงก่อน Completed (C-141/C-143)
• ใช้ข้อมูล GPS จาก ESP32 และ MPU6050 ผ่าน Pi เพื่อช่วยประเมินการหยุดนิ่ง โดยใช้หลายค่าต่อเนื่องและคุณภาพสัญญาณ ไม่สรุปจาก GPS ความเร็วศูนย์ครั้งเดียว; หาก GPS รถไม่พร้อมตรวจ Return Zone อาจใช้ GPS โทรศัพท์ผู้ขับช่วยเฉพาะการตรวจโซนตาม C-027/C-124 แต่ห้ามใช้แทนหลักฐานหยุดนิ่งหรือ Motor Ready ปิดจริง และหาก GPS รถที่เชื่อถือได้ชี้ว่าอยู่นอกโซนต้องยึด GPS รถ
• หากยืนยันการหยุดนิ่งไม่ได้ ให้เข้าสู่ Pending End ห้ามเริ่มรอบใหม่
• หากคำขอจบค้างและข้อมูลกลับมาน่าเชื่อถือ ให้ตรวจเงื่อนไขคืนรถและผลยืนยัน Motor Ready ปิดจริงก่อน Completed; หาก Return Zone ไม่พร้อม ให้ใช้ข้อยกเว้น Manager ตาม C-028 เมื่อผ่านคำขอ End/หยุดนิ่ง/ยืนยัน Motor Ready ปิดจริงพร้อมบันทึกเหตุผล; หากตรวจไม่ได้ ให้ Admin/Manager ตรวจรถจริงและดำเนินการปิดกรณีพิเศษตามสิทธิ์ (C-030) พร้อมบันทึกเหตุผล/เวลา/ผู้ยืนยัน
• การจัดการ Pending End ต้องไม่สั่งเปิด Motor Ready ใหม่โดยอัตโนมัติ และห้ามตัดกำลังขณะรถกำลังเคลื่อนที่; ต้องยืนยันการหยุดนิ่งและผลปิดจริงก่อนจบปกติ
7.5 ความผิดปกติระหว่างรอบ

หาก ESP32 รีสตาร์ตระหว่าง Active Session ต้องกู้สถานะจากข้อมูลท้องถิ่นและ/หรือเซิร์ฟเวอร์ ห้ามอนุญาตมอเตอร์ขึ้นใหม่อัตโนมัติเพราะรีสตาร์ต หากข้อมูลเซิร์ฟเวอร์กับรถไม่ตรงกัน ให้เซิร์ฟเวอร์เป็นหลักเมื่อออนไลน์ ระงับรอบใหม่และแจ้ง Admin/Manager โดยไม่ตัดกำลังรถที่กำลังขับจริง
08  การป้องกันคำสั่งและความมั่นคงปลอดภัย

8.1 ตัวตนรถต่อ Supabase

• Raspberry Pi มี Device ID และ Device Secret แบบสุ่มเฉพาะรถ ส่งผ่าน HTTPS ไปยัง Edge Functions
• Edge Functions ตรวจและจำกัดสิทธิ์ข้อมูลของรถ ใช้การเพิกถอน/หมุนรหัสลับได้
• ไม่เก็บ Supabase Service Role Key บนรถหรือฝังไว้ในเว็บสาธารณะ
• ทุกคำสั่งที่มีสิทธิ์สูง เช่น เริ่มรอบ อนุมัติสิทธิ์ แก้ Polygon ต้องตรวจ Role และ State ฝั่งเซิร์ฟเวอร์
8.2 ลายมือชื่อคำอนุมัติ (Digital Signature)

Edge Functions ลงลายมือชื่อให้ข้อมูล Vehicle ID, User ID, Session ID, Command ID, Number used once
(ค่าที่ใช้เพียงครั้งเดียว เพื่อป้องกันการนำคำสั่งเก่ากลับมาใช้ซ้ำ ) และความหมดอายุ แล้วส่งผ่าน Pi ให้ ESP32 ตรวจด้วย Public Key ที่ติดตั้งไว้ โดยกำหนดว่าการตรวจลายมือชื่อต้องครอบคลุมฟิลด์ทั้งหมดและรูปแบบการเข้ารหัสข้อมูลที่แน่นอน ขณะนี้ยังไม่ได้เลือกอัลกอริทึมและรูปแบบ Serialization(การแปลงข้อมูลให้อยู่ในรูปแบบที่จัดเก็บหรือส่งต่อได้ )
8.3 Challenge–Response

• ESP32 สร้าง Number used once (ค่าที่ใช้เพียงครั้งเดียว เพื่อป้องกันการนำคำสั่งเก่ากลับมาใช้ซ้ำ ) ใหม่จาก Cryptographically Secure Pseudorandom Number Generator (ระบบสร้างค่าสุ่มที่คาดเดาได้ยากสำหรับงานด้านความปลอดภัย) สำหรับการขอเริ่มรอบแต่ละครั้ง
• เซิร์ฟเวอร์ตรวจสิทธิ์ล่าสุดและเชื่อมคำอนุมัติกับ Nonce เฉพาะครั้ง
• ESP32 ยอมรับคำสั่งภายในช่วงเวลาท้องถิ่นสูงสุดเบื้องต้น 30 วินาที; สิทธิ์จอง 5 นาทีตรวจแยกที่เซิร์ฟเวอร์
• หาก ESP32 รีสตาร์ตต้องสร้างNumber used once (ค่าที่ใช้เพียงครั้งเดียว เพื่อป้องกันการนำคำสั่งเก่ากลับมาใช้ซ้ำ ) ใหม่และเริ่มกระบวนการใหม่; ไม่ยอมรับคำอนุมัติก่อนรีสตาร์ต
• บันทึก Command ID ที่ใช้แล้ว/สถานะที่จำเป็นเพื่อป้องกัน Replay และกรณีคำขอถูกส่งซ้ำ
8.4 ข้อควรระวังเชิงปฏิบัติ

การเปลี่ยน Pending Start → Active Session ต้องแยก Start Authorization (อนุมัติให้เริ่ม) ออกจาก Start Confirmation (ผลยืนยัน Motor Ready จริง); ต้องได้รับผลที่เชื่อถือได้จาก ESP32 และสัมพันธ์กับ Session ID/Command ID เดียวกันก่อนเซิร์ฟเวอร์บันทึก Active หากสถานะไม่ชัดเจนให้กันการเริ่มรอบใหม่และประสานสถานะ ห้ามตัดกำลังรถที่กำลังเคลื่อนที่เพื่อแก้ฐานข้อมูล; วิธีตรวจยืนยัน Motor Ready ยังต้องออกแบบและพิสูจน์กับวงจรจริง
09  ระบบ AI: YOLO Segmentation, กล้อง และ IMU

9.1 อุปกรณ์และรูปแบบโมเดล

Raspberry Pi 5 RAM 4GB ใช้ YOLO Segmentation รุ่นขนาดเล็ก วิเคราะห์ภาพจาก Raspberry Pi Camera Module 3 Wide (ตัวเลือกเบื้องต้น) และข้อมูล MPU6050 ผ่าน I²C โดยกล้องต้องยึดกับโครงรถด้านหน้า ไม่ติดแฮนด์
9.2 หน้าที่และข้อจำกัด

• แยกพื้นที่ถนน แนวเส้นช่องทาง และขอบไหล่ทางด้วย Segmentation Mask (ภาพที่ระบุว่าพิกเซลแต่ละจุดเป็นส่วนของวัตถุหรือพื้นที่ประเภทใด)
• ปรับเทียบกล้องและขนาดรถ ประกอบข้อมูลการเอียงจาก IMUเพื่อประเมินระยะห่างจากขอบนอกตัวรถถึงขอบไหล่ทางเป็นเมตร
• ตรวจ Lane Departure เมื่อขอบตัวรถแตะหรือข้ามเส้นช่องทางตามเกณฑ์หลายเฟรม และใช้แนวโค้งลด False Positive (ระบบแจ้งว่าพบสิ่งที่ต้องตรวจจับ ทั้งที่จริงไม่มี)
• ตรวจ Near Shoulder (รถเข้าใกล้ไหล่ทาง)  จากระยะเตือนที่กำหนดตาม Pilot โดยวัดจริงเทียบเทปวัดระยะ
• เมื่อเห็นเส้นถนนไม่ได้/ความเชื่อมั่นต่ำ ให้แสดง AI temporarily unavailable (ระบบ AI ไม่พร้อมใช้งานชั่วคราว)  และไม่สร้างคำเตือนจากผลที่ไม่น่าเชื่อถือ
• ใช้งานด้านการตรวจจับเฉพาะกลางวันและถนนที่มีเส้นหรือแนวไหล่ทางชัดเจน ไม่รับรองกลางคืน สภาพเส้นเลือนราง หรือการแยกการเปลี่ยนเลนโดยเจตนาทุกกรณี
• ไม่สั่งลดกำลัง/เบรก/เลี้ยว/หยุดรถตามผล AI ผู้ขับยังควบคุมรถด้วยตนเอง
• ระบบแจ้งเตือนไม่ทำงานระหว่างที่รถมีการเอียงประมาณ 15 องศา หรือมากกว่านั้น เพื่อทำให้ไม่ขัดจังหวะการขับขี่
9.3 ช่วงเวลาประมวลผล

Raspberry Pi ต้องเปิดเครื่องอยู่ตลอด แต่เริ่มกล้อง/YOLO เฉพาะขณะมีการขอเริ่มรอบหรือ Active Session(รอบการใช้งานรถที่กำลังดำเนินอยู่)  ไม่ประมวลผลภาพตลอดขณะจอดว่าง; หาก AI Process ขัดข้อง ให้พยายามเริ่ม Process ใหม่ โดยไม่รีบูต Raspberry Pi ทั้งเครื่องและไม่ตัดกำลังมอเตอร์

9.5 ความสดใหม่ของข้อมูล

ใช้ Latest-Frame Processing และ Timestamp ของเฟรม ไม่สะสมคิวภาพเก่า หากผล Segmentation ช้าจนเกินเกณฑ์ที่สอดคล้องกับเป้าหมายแจ้งเตือน ไม่เกิน 1 วินาที ให้ทิ้งผลนั้นและส่งสถานะ AI ไม่พร้อมชั่วคราว Raspberry Pi ส่ง Event ID, Sequence Number และอายุเหตุการณ์ทาง UART; ESP32 ต้องปฏิเสธเหตุการณ์เก่า/ซ้ำ รวมเวลารอคิวเสียงด้วย
9.6 การวัดผล AI

• Dataset มี mask สำหรับถนน เส้นช่องทาง/ขอบไหล่ทาง และป้ายกำกับ Event Episode (ช่วงเหตุการณ์ต่อเนื่องหนึ่งครั้ง)  สำหรับ Lane Departure
(รถเบี่ยงออกจากช่องทางเดินรถ)  / Near Shoulder(รถเข้าใกล้ไหล่ทาง)
• แบ่ง Train/Validation/Test ตามวิดีโอหรือ Session ที่เป็นอิสระ; ห้ามเฟรมที่ต่อเนื่องกันข้ามชุด
• ผู้ประเมินสองคนทำ ผลเฉลยจริง(Ground Truth) โดยอิสระและหารือเมื่อผลไม่ตรงกัน
• ใช้ Macro F1 ไม่น้อยกว่า 90% ของสองประเภทเหตุการณ์ รายงาน Precision/Recall/F1 แยกรายประเภท และตั้งเกณฑ์ขั้นต่ำของแต่ละประเภทจาก Pilot ก่อน Holdout (ชุดข้อมูลที่กันไว้ทดสอบโมเดล)
• ความคลาดเคลื่อนระยะทางประเมินแยกด้วย Mean Absolute Error (ค่าเฉลี่ยของความคลาดเคลื่อนแบบสัมบูรณ์ ) และกรณีค่าคลาดสูง เทียบระยะจริงหลายระยะและหลายมุมเอียง; ล็อกเกณฑ์ก่อน Holdout (ชุดข้อมูลที่กันไว้ทดสอบโมเดล)
• ความหน่วง AI จากภาพ/ตรวจจับจนแจ้งเตือนเป้าหมาย ไม่เกิน 1 วินาที; วัดเวลาทั้ง Pipeline (ลำดับขั้นตอนการประมวลผลข้อมูล)  จริง ไม่ใช้ค่า FPS อย่างเดียว
• บันทึกวิดีโอเฉพาะระหว่างการทดสอบที่ได้รับอนุญาต ไม่เก็บวิดีโอหรือภาพระหว่างการใช้งานทั่วไป
9.7 แนวทางเพิ่มประสิทธิภาพ

ปรับความละเอียดภาพ ใช้โมเดลเล็ก Runtime ที่เหมาะสม เช่น NCNN และ Quantization(การลดความละเอียดของตัวเลขในโมเดล) โดยทดสอบความแม่นยำและระยะทางใหม่ทุกครั้ง หากยังไม่ถึงเกณฑ์จึงพิจารณา AI Accelerator(อุปกรณ์ที่ช่วยเร่งการประมวลผล AI)  ที่มีความเข้ากันได้จริงกับ YOLO Segmentation รุ่นที่เลือก
10  ระบบเสียงแจ้งเตือนภาษาไทย

10.1 การทำงาน

ESP32-S3 เก็บไฟล์เสียงภาษาไทยไว้ใน Flash และเล่นผ่าน I²S → MAX98357A → ลำโพงภายนอกทนสภาพอากาศได้โดยไม่พึ่งอินเทอร์เน็ตหรือ Raspberry Pi ในส่วนเหตุการณ์ที่ ESP32 ทราบเอง
10.2 ลำดับความสำคัญ

• อันดับสูง: BMS/ความผิดปกติฉุกเฉินที่ระบบรู้จัก
• AI Lane Departure / Near Shoulder (AI ตรวจพบรถออกนอกเลน / เข้าใกล้ไหล่ทาง)  โดยเหตุการณ์เข้าใกล้ไหล่ทางความเสี่ยงสูงมาก่อนการข้ามเส้นทั่วไป
• GPS/Geofencing(รั้วเสมือนจริง) และสถานะสำคัญอื่น
• การแจ้งเตือนทั่วไป เช่น แบตเตอรี่ต่ำ/ชาร์จ/ชาร์จเต็ม ตามเกณฑ์เดิม
10.3 กติกาคิวเสียง

• กรณี Lane Departure (ตรวจพบรถออกนอกเลน) และ Near Shoulder(เข้าใกล้ไหล่ทาง) เกิดพร้อมกัน บันทึกทั้งสองเหตุการณ์ แต่เล่นเสียงที่มีความเสี่ยงสูงสุดเพียงหนึ่งเสียง
• เล่นครั้งแรกเมื่อยืนยันเหตุการณ์; หากยังอันตรายให้เล่นซ้ำหลัง Cooldown(ช่วงเวลาพักก่อนระบบจะแจ้งเตือนเหตุเดิมอีกครั้ง)  ที่กำหนดจาก Pilot ไม่เล่นทุกเฟรม
• Event Episode(ช่วงเหตุการณ์ต่อเนื่องหนึ่งครั้ง)  ต่อเนื่องนับหนึ่งเหตุการณ์จนกลับปกติตามเกณฑ์
• ไม่เล่นเสียง AI เก่าหรือหมดอายุและไม่ใช้เสียง AI ขัดจังหวะ BMS
• ผู้ขับปิดเสียงหรือปรับต่ำกว่าระดับมาตรฐานไม่ได้; Admin/ทีมพัฒนาตั้งและทดสอบเสียง
• หากระบบเสียงเสีย ยังอนุญาตให้ทุกบทบาทเริ่มรอบได้ตามเงื่อนไขอื่น แจ้ง Dashboard และ Admin/Manager; ไม่มี LED หรือจอแจ้งเตือนเสริม
[ตารางจากเอกสาร Word]
ความเสี่ยงที่ยอมรับ เมื่อเสียงเสีย ผู้ขับอาจไม่ได้รับคำเตือนทันที เพราะได้ตัดช่องทาง LED/หน้าจอสำรองออกแล้ว ESP32 อาจยืนยันเสียงจริงจากลำโพงไม่ได้ทุกกรณี จึงต้องระบุข้อจำกัดนี้ในการประเมินความเสี่ยง

11  GPS, ระยะทาง และ Geofencing

11.1 การวัดตำแหน่งและระยะทาง

• ใช้ ATGM336H บน ESP32 สำหรับพิกัดและความเชื่อมั่น GNSS; ขณะ Active Session ออนไลน์อัปเดตตำแหน่งไปยังเว็บทุกไม่เกิน 10 วินาที
• ขณะจอดใช้ความถี่อ่าน GPS ต่ำกว่าขณะขับ โดยกำหนดค่าจาก Pilot; Dashboard ต้องแสดงเวลาอัปเดตล่าสุดและแจ้งข้อมูลค้าง
• คำนวณระยะทางสะสมจากช่วงพิกัดที่ผ่านการตรวจความถูกต้องเท่านั้น; ไม่ลากเส้นข้ามช่วงไม่มีสัญญาณ
• เมื่อข้อมูลระยะทางบางส่วนขาด ให้แสดง “ข้อมูลระยะทางไม่ครบถ้วน”; หากไม่มีข้อมูลเลยแสดง “ไม่มีข้อมูลระยะทาง” ไม่ใช่ 0 กิโลเมตร
11.2 Polygon และสิทธิ์

Main Polygon คือรูปทรงขอบเขต Main Geofence (พื้นที่ใช้งานหลัก); Return Zone คือพื้นที่คืนรถแยกต่างหาก ไม่ใช่ชื่ออื่นของ Main Geofence (C-024). Admin สร้างและแก้ไข Polygon หลักเพียงหนึ่งชุดจากเว็บ ส่งเวอร์ชันที่ตรวจสอบได้ไป Raspberry Pi แล้ว ESP32 รับและจัดเก็บ หากเพิ่งติดตั้งและยังไม่มี Polygon นักศึกษาและบุคลากรเริ่มรอบไม่ได้ ส่วน Manager เริ่มได้ตามเงื่อนไขอื่นพร้อมแสดงคำเตือน
แก้ไข Polygon ใหม่ได้เฉพาะรถจอด ออนไลน์ และไม่มี Session ใช้งาน เมื่อข้อมูลไม่ผ่านการตรวจสอบให้ Rollback เวอร์ชันเดิม; ขณะออฟไลน์ใช้ Polygon ล่าสุดที่ตรวจสอบผ่าน
11.3 ออกนอกพื้นที่

• นักศึกษาและบุคลากรที่ GPS ยืนยันได้ว่าออกนอก Polygon ต่อเนื่องเป็นเวลา 5 นาทีได้รับการเตือนบนรถและแจ้งผู้ดูแล
• ใช้ Hysteresis(กลไกป้องกันสถานะสลับไปมาถี่ ๆ)  และจำนวน Fix ต่อเนื่องที่กำหนดหลัง Pilot เพื่อลดการตัดสินผิดจากพิกัดลอย
• ไม่ใช้ Geofencing เป็นเหตุให้จำกัดแรงบิด ลดกำลัง จำกัดความเร็ว หรือสั่งตัดกำลังมอเตอร์ระหว่างขับ แม้ VOTOL จะรองรับฟังก์ชันดังกล่าว; ให้ใช้เสียงแจ้งเตือนจาก ESP32 และข้อความเว็บไซต์ตาม C-113
• เมื่อรถออกนอกเขต ให้บันทึกเหตุการณ์ แจ้ง Admin/Manager และแจ้งผู้ขับ; การห้ามเริ่มรอบใหม่ให้ยึดสิทธิ์ตาม C-115 และสถานะ GPS ตาม C-116
• Manager ยกเว้นข้อจำกัดการเริ่มใหม่จากการอยู่นอก Main Geofence ตาม C-115 แต่ยังต้องออนไลน์และผ่านการตรวจสอบความปลอดภัยอื่นทั้งหมด; ให้บันทึก Audit Log (บันทึกการตรวจสอบ) เมื่ออนุญาตตามข้อยกเว้น
• เมื่อรถกลับเข้า Main Geofence (ขอบเขตพื้นที่ใช้งานหลัก) ให้ใช้พิกัดที่เชื่อถือได้ยืนยันและบันทึกสถานะกลับเข้าเขต; ไม่มีการคืนกำลังจากคำสั่งลดกำลัง Geofencing เพราะระบบจะไม่ลดกำลังมอเตอร์จากเหตุนี้
11.4 GPS ไม่พร้อม

เมื่อ GPS ของรถไม่มี Fix (พิกัดที่ตรวจสอบแล้วว่าน่าเชื่อถือ) หรือพิกัดไม่น่าเชื่อถือขณะขอเริ่ม Session ใหม่: Student และ Employee ห้ามเริ่ม; Manager อาจเริ่มได้เมื่อออนไลน์และผ่านเงื่อนไขความปลอดภัยอื่นทุกข้อ; Admin ไม่ใช่บัญชีขับรถ (C-116). ระหว่าง Active Session เมื่อ GPS สูญหายต้องไม่ตัดกำลังมอเตอร์กะทันหัน; ให้ระบุความไม่พร้อมของข้อมูลตำแหน่งและไม่ใช้พิกัดที่ไม่น่าเชื่อถือตัดสิน Geofencing
12  BMS, การชาร์จ และพลังงาน

12.1 BMS และการเริ่มรอบ

• ESP32 อ่าน State of Charge(%แบตเตอรี่) สถานะการชาร์จ/ชาร์จเต็มและ Fault จาก BMS เดิม
• หาก แบตเตอรี่ ต่ำกว่า 10% ห้ามทุกบทบาทเริ่มรอบใหม่; ระดับปลดบล็อกให้กำหนดจาก Pilot
• หากอ่าน BMS ไม่ได้หรือข้อมูล BMS ผิดปกติ ห้ามทุกบทบาทเริ่มรอบใหม่
• หากตรวจว่ากำลังชาร์จหรือสายชาร์จยังต่ออยู่ ห้ามเริ่มรอบใหม่; การตรวจสายชาร์จจริงขึ้นกับวงจรเดิมที่ตรวจได้
• ขณะขับ หากแบตเตอรี่ต่ำหรือ BMS เกิดปัญหา ให้แจ้งเตือนและแนะนำหยุดอย่างปลอดภัย ไม่ตัดกำลังจากระบบเสริม; ระบบป้องกันไฟฟ้าของ BMS เดิมยังมีผลตามการออกแบบรถ
• แสดงสถานะ BMS บนเว็บตามเป้าหมายเวลาที่กำหนด 30 วินาที; แจ้งชาร์จและชาร์จเต็มด้วยเสียง/เว็บตามข้อมูลที่มี
12.2 พลังงานขณะจอด

ESP32 และ Raspberry Pi ยังรับไฟจาก DC-DC เดียวกันตราบที่แบตเตอรี่จ่ายได้; Pi ไม่ปิดเครื่องแต่หยุด YOLO ลดภาระและความถี่สื่อสารตามโหมดจอด ตรวจ State of Charge(%คงเหลือแบตเตอรี่) และแจ้ง Admin/Manager ล่วงหน้า ผู้ดูแลต้องชาร์จรถก่อนพลังงานหมดจริง วัดพลังงานและระยะเวลาจอดจริงก่อนกำหนดระดับแจ้งเตือน
12.3 กล่องและสภาพอากาศ

กล่องอุปกรณ์เป้าหมาย IP65 พร้อม Cable Gland/Connector (ข้อต่อรัดสายไฟกันน้ำ / หัวต่อสายไฟ)
กันน้ำ ระบายความร้อน Raspberry Pi โดยรักษาความสามารถกันน้ำ ทดสอบน้ำและอุณหภูมิของชุดประกอบจริง ยังไม่เพิ่มระบบตัดสินจัดการอุณหภูมิสูงแบบอัตโนมัติ
13  เครือข่าย การทำงานออฟไลน์ และการซิงก์

13.1 การสื่อสารปกติ

• Pi ใช้ LTE/4G กับ SIM เป็นเส้นทางอินเทอร์เน็ตเดียวของรถ และส่งข้อมูลผ่าน Supabase Edge Functions/Realtime/HTTPS
• Pi รับคำสั่งผ่าน Realtime แล้วเรียก Edge Functions ตรวจสิทธิ์/Time to Live(ระยะเวลาที่ข้อมูลหมดอายุ) ก่อนส่ง ESP32
• ESP32 ส่ง Acknowledgment (ข้อความตอบกลับว่าได้รับคำสั่งหรือข้อมูลแล้ว) พร้อม Command ID กลับ Pi; หาก Acknowledgment  หายให้ส่งซ้ำด้วย Command ID เดิมภายใน Time to Live(ระยะเวลาที่ข้อมูลหมดอายุ)
• Pi reconnect ต้องดึงคำสั่งที่ค้างใหม่ และปฏิเสธคำสั่งหมดอายุหรือไม่สอดคล้องสถานะ; ไม่เริ่มรอบโดยอัตโนมัติหลัง reconnect
• กำหนด Heartbeat ระยะขับ/ระยะจอดตาม Pilot; Dashboard แสดงเวลาเชื่อมต่อล่าสุดและ Offline ที่ไม่สรุปว่า ESP32 เสียแน่นอน
13.2 เมื่อ 4G หรือ Pi ขัดข้อง

รถจะถือว่าไม่สามารถติดต่อ Supabase ได้สำหรับการเริ่มรอบใหม่ทุกบทบาท แต่ Active Session ยังคงบันทึกข้อมูลใน ESP32 และทำงานเฉพาะระบบที่มีข้อมูลท้องถิ่น เช่น BMS, GPS, เสียงเตือนที่มีข้อมูล เก็บประวัติและซิงก์ในภายหลัง โดยไม่ตัดมอเตอร์กลางทางจากความขัดข้องของเครือข่าย
13.3 ข้อมูลออฟไลน์

• ข้อมูล GPS/BMS ตามปกติระหว่างขับออฟไลน์บันทึกทุก 60 วินาที และบันทึกเหตุการณ์สำคัญทันที
• ใช้หน่วยความจำถาวรรองรับอย่างน้อย 24 ชั่วโมงโดยไม่สูญหายเมื่อไฟดับหรือ ESP32 รีสตาร์ต
• ก่อนใกล้เต็มให้ลดความถี่บันทึกข้อมูลปกติชั่วคราวและรักษาความสำคัญของ Event Log พร้อมแสดงว่าข้อมูลอาจไม่ครบ
• หากพื้นที่เต็มจนไม่สามารถเก็บ Event Log ที่สำคัญ ให้บล็อกการเริ่มรอบใหม่ทุกบทบาท แต่ Active Session
(รอบการใช้งานรถที่กำลังดำเนินอยู่)  ดำเนินต่ออย่างปลอดภัย
• เมื่อพื้นที่เขียนข้อมูลกลับมาพร้อมและการซิงก์มีสถานะดี ให้คืนสิทธิ์เริ่มรอบโดยอัตโนมัติหากเงื่อนไขอื่นผ่าน
13.4 ความถูกต้องการซิงก์

แต่ละรายการใช้ Session ID + Sequence Number ที่เพิ่มต่อเนื่อง และมี End-of-Session Manifest ระบุจำนวนรายการที่ควรมี Supabase รับรอง Acknowledgment (ข้อความตอบกลับว่าได้รับคำสั่งหรือข้อมูลแล้ว) หลัง Commit จริงเท่านั้น; ESP32 ลบได้เฉพาะข้อมูลที่บันทึก Acknowledgment อย่างทนทานแล้ว ไม่สร้างข้อมูลซ้ำเมื่อส่งอีกครั้ง และไม่ระบุ Sync Complete(ซิงก์ข้อมูลเสร็จสมบูรณ์)  หากยังมีลำดับขาด
เป้าหมายการซิงก์หลังกลับออนไลน์ภายใน 30 วินาทีต้องระบุขนาดชุดข้อมูลทดสอบและเครือข่ายที่ใช้จริง มิฉะนั้นไม่สามารถตีความว่าข้อมูลค้างเต็ม 24 ชั่วโมงทุกกรณีจะส่งครบภายใน 30 วินาที
13.5 เวลาและความไม่แน่นอน

เมื่อออนไลน์ใช้เวลาจากเซิร์ฟเวอร์ Supabase เป็นเวลาอ้างอิง; ออฟไลน์ ESP32 ใช้เวลาในเครื่อง หากรีสตาร์ตแล้วไม่มีเวลาที่เชื่อถือได้ ต้องบันทึกสถานะ Timestamp Uncertain (เวลาที่บันทึกข้อมูลยังไม่แน่นอน)  และไม่ใช้เวลาที่ไม่แน่นอนเป็นฐานให้เกิดคำสั่งอันตราย ส่วน Timer ต่อเนื่องที่อุปกรณ์ยังทำงานใช้ Monotonic Clock

14.2 การแสดงและเข้าถึงข้อมูล

• ผู้ขับเห็นเฉพาะรอบของตัวเอง; Manager เห็นข้อมูลที่จำเป็นดูแลรถ; Admin เข้าถึงประวัติตามหน้าที่
• Row Level Security (การกำหนดสิทธิ์เข้าถึงข้อมูลเป็นรายแถว) และ Edge Functions ต้องบังคับสิทธิ์ทุกจุดอ่าน เขียน ลบ และส่งออก; ห้ามใช้การซ่อนเมนูเป็นมาตรการเพียงอย่างเดียว
• ผู้ใช้รับทราบประกาศข้อมูลส่วนบุคคลและข้อตกลงการใช้รถก่อนเริ่มครั้งแรก บันทึก Version+User+Timestamp และรับทราบใหม่เมื่อมีการเปลี่ยนแปลงสำคัญโดยไม่รบกวน Active Session(รอบการใช้งานรถที่กำลังดำเนินอยู่)
• ไม่เก็บวิดีโอ/ภาพขับปกติ เก็บเพียง Event Log; วิดีโอทดสอบต้องเป็นรอบที่ได้รับอนุญาต
14.3 การปิดใช้งานบัญชีตนเอง

ผู้ใช้ปิดใช้งานบัญชีตนเองผ่านเว็บไซต์ได้เมื่อไม่มี Reservation, Pending Start, Active Session, Pending End หรือธุรกรรม Session และข้อมูลซิงก์/ประสานสถานะค้างอยู่; หากมีรายการค้าง ต้องยกเลิกคำขอที่ยังไม่เริ่ม หรือคืนรถจน Completed ให้เรียบร้อยก่อน ไม่ปิดบัญชีพร้อมยกเลิกคำขออัตโนมัติ. การปิดบัญชีเป็นการยุติสิทธิ์ใช้งานบัญชีเดิม ไม่ใช่คำสั่งลบประวัติ Session/GPS/เหตุการณ์ถาวร; ประวัติที่ต้องเก็บยังคงอยู่ตามนโยบายและกฎหมาย โดยข้อมูลอ้างอิงที่เชื่อมโยงตัวตนของบัญชีที่ปิดให้เฉพาะ Admin เข้าถึง. คำขอเข้าถึง แก้ไข หรือลบข้อมูลส่วนบุคคลต้องยื่นผ่านแบบฟอร์ม Data Subject Request แยกต่างหากเพื่อให้ Admin พิจารณาตาม C-094; บัญชีที่ปิดแล้วไม่เปิดกลับมา และการสมัครใหม่ไม่โอนประวัติหรือบัตร NFC เดิมโดยอัตโนมัติ (C-090–C-094)
14.4 ตรวจประวัติเมื่อสมัครใหม่

ระบบตรวจชื่อ–นามสกุลและเบอร์โทรกับข้อมูลอ้างอิงเดิมเพื่อแจ้ง Admin หากอาจเป็นผู้ที่เคยถูกระงับสิทธิ์ ไม่อนุมัติหรือปฏิเสธอัตโนมัติจากข้อมูลตรงกันเพียงอย่างเดียว; บัญชีใหม่ยัง Pending จน Admin ตรวจสอบ
14.5 การลบประวัติการเดินทางโดย Admin

• ประวัติ GPS และเหตุการณ์ของ Session ที่ Admin เลือกลบต้องเข้า Recycle Bin เป็นชุดเดียวกันเป็นเวลา 30 วัน สามารถคืนเป็นชุดก่อนลบถาวร
• ลบได้หลังตรวจ Sync Complete หรือผ่านกระบวนการ การจัดการข้อมูลที่เสียหายหรือไม่ครบ ที่ Admin ตรวจสอบหลักฐานอย่างชัดเจน; ห้ามอ้าง Sync Complete เมื่อข้อมูลต้นทางไม่ครบ
• เก็บ Audit Log(บันทึกการตรวจสอบ) ขั้นต่ำของใครทำอะไรเมื่อใด แต่ไม่คัดลอก GPS ที่ลบไว้ใน Audit Log
• ต้องป้องกันการซิงก์จาก ESP32 นำข้อมูลที่ลบถาวรแล้วกลับเข้าระบบ
หมายเหตุ: การปิดใช้งานบัญชีไม่ใช่คำสั่งลบประวัติการเดินทาง และไม่ใช่คำขอลบข้อมูลส่วนบุคคล; การลบประวัติโดย Admin ในหัวข้อ 14.5 และการขอใช้สิทธิข้อมูลส่วนบุคคลเป็นกระบวนการแยกกันตาม C-090–C-094 และกฎหมายที่เกี่ยวข้อง
เมื่อผู้ใช้ปิดบัญชี ประวัติ Session/GPS และเหตุการณ์เดิมที่ต้องเก็บไม่ถูกลบอัตโนมัติ; เฉพาะ Admin เท่านั้นที่เข้าถึงข้อมูลอ้างอิงซึ่งเชื่อมโยงกลับถึงตัวตนของบัญชีที่ปิดตามสิทธิ์และวัตถุประสงค์ที่กำหนด ส่วน Manager ดูข้อมูลการดำเนินงานได้เท่าที่สิทธิ์เดิมอนุญาต แต่ไม่มีสิทธิ์เข้าถึงข้อมูลอ้างอิงเชื่อมตัวตนดังกล่าว. เมื่อสิ้นสุดโครงการให้ดำเนินการตาม C-094 โดยคำนึงถึงข้อยกเว้นและหน้าที่ตามกฎหมาย

15.1 หลัก UX ที่ต้องคำนึง

• Responsive สำหรับโทรศัพท์ แท็บเล็ต และคอมพิวเตอร์
• แสดงเวลาข้อมูลล่าสุดอย่างเด่นชัด เพื่อไม่ให้ตำแหน่งหรือ State of Charge  ค้างดูเหมือน Realtime
• แยกสถานะ Reserved / Pending Start / Active / Pending End / Completed ชัดเจน พร้อมสาเหตุที่เริ่มไม่ได้
• คำขอเริ่มผ่านเว็บ/NFC ต้องได้รับการอนุมัติออนไลน์และยืนยันผู้ใช้อยู่ใกล้รถก่อน Motor Ready; ไม่ใช้ลำดับสวิตช์ OFF→ON (C-136–C-139)
• เมื่อปิดบัญชีไม่ได้ ให้บอกเหตุค้าง เช่น Reservation, Pending End หรือ Unsynced Records; ไม่ปิดโดยไม่แจ้งเหตุ
• ไม่พัฒนาการดาวน์โหลดหรือส่งออกรายงาน Excel/CSV/PDF; แสดงรายงานเฉพาะบนเว็บไซต์ตาม C-071
16  การบำรุงรักษา การอัปเดต และการคืนใช้งาน

• อัปเดต ESP32 และ Raspberry Pi ที่ตัวรถโดย Admin/ทีมพัฒนาที่ได้รับมอบหมายเท่านั้น ไม่ใช่ OTA ผ่านเว็บ
• เข้าบำรุงรักษาได้เมื่อรถจอด ไม่มี Active/Pending Session และไม่เปิดให้เริ่มรอบใหม่
• ก่อนอัปเดตตามปกติต้องซิงก์ข้อมูลครบและมีหลักฐาน Acknowledgment (ข้อความตอบกลับว่าได้รับคำสั่งหรือข้อมูลแล้ว); ถ้าอุปกรณ์เสีย ให้สำรองข้อมูลที่อ่านได้และบันทึกหลักฐาน Data Loss หากกู้ไม่ได้
• ตรวจสอบไฟล์อัปเดต เวอร์ชัน แหล่งที่มา และ Public Key ที่เปลี่ยน
• หลังอัปเดตทดสอบ ESP32, Pi, UART, LTE/Supabase, NFC, BMS, คำอนุมัติลงลายมือชื่อ และ AI ตามบทบาท เมื่อผ่านแล้ว Admin หรือทีมพัฒนาที่ได้รับสิทธิ์จึงออกจาก Maintenance
• หากไม่ผ่านให้ห้ามรอบใหม่และแก้ไข/คืนเวอร์ชันที่ผ่านทดสอบ การทดสอบต้องไม่สร้างการขับเคลื่อนที่ไม่ปลอดภัย
• Maintenance Mode ไม่ใช่ทางลัดขับจริง หากต้องขับทดสอบให้กลับสู่โหมดปกติและใช้บัญชีผู้ขับยืนยัน NFC/เว็บ
• หากตรวจมอเตอร์พร้อมทำงานโดยไม่มี Session ที่ได้รับอนุมัติจากสัญญาณที่น่าเชื่อถือ ให้แจ้ง Admin/Manager บันทึกเหตุ และระงับรอบใหม่จนตรวจรถจริง; Manager หรือ Admin ปลดได้หลังตรวจและบันทึกผล ไม่ใช่สั่งมอเตอร์ทำงาน

17.2 แยกเกณฑ์ความสำเร็จออกจากเงื่อนไขความปลอดภัย

อัตราผ่าน 90% ของงานระบบไม่ใช่เหตุอนุญาตให้ขับหากยังมีความผิดปกติที่เสี่ยงต่อความปลอดภัย โดยเฉพาะ E-lock/Enable (วงจรอนุญาตให้มอเตอร์พร้อมทำงาน), คันเร่งเป็นศูนย์, ความหยุดนิ่ง และ BMS (ระบบจัดการแบตเตอรี่); โครงการยืนยันว่าจะไม่มี Bench Test (การทดลองบนแท่น) แต่ต้องตรวจเอกสาร/วงจร สภาพรถ และการทำงานด้านความปลอดภัยที่จำเป็นก่อน Real Riding Test (การทดลองขับจริง) ในพื้นที่ปิดที่ได้รับอนุญาต หากไม่สามารถพิสูจน์ความปลอดภัยที่จำเป็นได้ ห้ามเริ่มการทดลองขับจริง
การกำหนดค่าทางเทคนิคของวงจรมอเตอร์และวิธีพิสูจน์ยังต้องตรวจสอบกับรถจริงก่อนทดลอง; แต่ผู้มีหน้าที่ร่วมพิจารณาความพร้อมก่อน Pilot Test (การทดลองใช้ระบบต้นแบบ) ได้ยืนยันเป็นสมาชิกทีมพัฒนา 4 คนและอาจารย์ที่ปรึกษา โดยต้องได้รับอนุญาตพื้นที่และปฏิบัติตามระเบียบมหาวิทยาลัยด้วย ไม่ถือว่าการลงมติเป็นหลักฐานว่ารถผ่านการตรวจความปลอดภัยแล้ว
17.3 เคสทดสอบที่ควรครอบคลุม

• ผู้ใช้สองคนอนุมัติพร้อมกันต้องไม่เกิด Reservation ซ้อน
• NFC UID ถูกยกเลิก / บัญชี Suspended ระหว่างรอ 5 นาที ต้องไม่เริ่มรอบ
• คำสั่งหมดอายุ Nonce ไม่ตรง Digital Signature ผิด Command ID ซ้ำ ต้องไม่เริ่มรอบ
• ผู้ใช้ยังไม่มี Driving Permission หรือยืนยันความใกล้รถไม่ได้ ต้องไม่ให้ Motor Ready แม้ Account Approved
• คันเร่งไม่ศูนย์ รถยังเคลื่อนที่ แบตเตอรี่ <10% BMS เสีย กำลังชาร์จ ต้องไม่เริ่มรอบ
• Pi/4G หายระหว่างขับ, ESP32 รีสตาร์ต, UART ขาด ต้องไม่ทำให้วงจรเสริมตัดมอเตอร์กะทันหัน

• กล้องผิดมุม, IMU ขัดข้อง, YOLO ภาพค้าง, Event AI ซ้ำ/เก่า, AI สองเหตุการณ์พร้อมกัน

19.1 ข้อจำกัดที่ต้องแจ้งผู้ใช้งานและอาจารย์ที่ปรึกษา

• ระบบ AI เป็นเพียงผู้ช่วยเตือน ไม่ทดแทนการมองถนนและตัดสินใจของผู้ขับ
• กล้องเดี่ยวและ IMU อาจประเมินระยะคลาดเคลื่อนในบางมุม สภาพแสง และถนนที่ไม่มีเส้นชัดเจน
• NFC UID-only อาจถูกคัดลอก และไม่มี MFA ตามขอบเขตที่ผู้ใช้เลือก
• หากระบบเสียงเสีย ผู้ขับอาจไม่มีช่องทางแจ้งเตือนบนตัวรถแม้เว็บแจ้งผู้ดูแล
• หาก Supabase สูญหายหลังข้อมูล local ถูกลบแล้ว อาจกู้ข้อมูลไม่ได้เพราะไม่ได้พัฒนาระบบสำรอง
• การเก็บประวัติ GPS ที่เชื่อมโยงตัวตนหลังปิดบัญชียังเป็นการประมวลผลข้อมูลส่วนบุคคล ต้องมีเหตุผลและระยะเวลาที่เหมาะสมตาม C-094 และกฎหมายที่เกี่ยวข้อง

ภาคผนวก C — มติข้อกำหนดเพิ่มเติม (14 ต.ค. 2569)

สำคัญ: ภาคผนวกนี้เป็นมติล่าสุดที่ยืนยันจากบทสนทนา ข้อกำหนดในภาคผนวก C มีผลแทนข้อความเดิมเฉพาะจุดที่ขัดกัน โดยเฉพาะ Geofence ไม่ลดกำลังมอเตอร์ขณะขับ การปิดใช้งานบัญชี และการแสดงข้อมูลบนเว็บ
โครงการ: ระบบรถจักรยานยนต์ไฟฟ้าสาธารณะพร้อมระบบ AI ช่วยเตือนการขับขี่
สถานที่: มหาวิทยาลัยวลัยลักษณ์ | รถต้นแบบ: 1 คัน | ทีมงาน: 4 คน
วันที่ปรับปรุง: 14 ตุลาคม 2569 | ฐานอ้างอิง: เอกสารรวบรวมข้อกำหนดวันที่ 13 ตุลาคม 2569 และการตัดสินใจต่อเนื่องในการสนทนา
สถานะ: REQUIREMENTS WORKING BASELINE — ไม่ใช่หลักฐานว่าซอฟต์แวร์ วงจร หรือฮาร์ดแวร์พัฒนาและทดสอบแล้ว
C.0 วิธีอ่านเอกสารและลำดับความสำคัญ

CONFIRMED = ผู้ใช้ยืนยันข้อกำหนดแล้ว; PENDING DECISION = ยังไม่ได้เลือก; PENDING TEST / SAFETY REVIEW = ต้องตรวจพิสูจน์ก่อนนำไปใช้จริง; NOT STARTED = ไม่ได้ยืนยันว่าลงมือทำแล้ว
เมื่อข้อกำหนดเก่าในเอกสารวันที่ 13 ต.ค. ขัดกับมติล่าสุดในภาคผนวก C ให้ยึดมติล่าสุดที่ยืนยันแล้ว เฉพาะหัวข้อที่ขัดกัน; ส่วนอื่นของต้นฉบับยังคงเป็นฐานออกแบบ
กรณีการยอมรับในเชิง UX/นโยบายอาจยังมีข้อจำกัดทางกฎหมายหรือความปลอดภัย ไม่ให้ข้ามการตรวจสอบจริง
ไม่สมมติค่าตัวเลขจาก Pilot Test ไม่ตีความข้อที่ยังไม่ได้ตอบเป็นมติ และไม่อ้างว่าฟังก์ชันพัฒนาแล้ว
C.1 หลักการสถาปัตยกรรมและ Session ที่ต้องรักษาไว้

C-001 [CONFIRMED] ระบบประกอบด้วยรถไฟฟ้าต้นแบบหนึ่งคัน; ESP32-S3 ดูแล NFC PN532, GPS ATGM336H, BMS, เงื่อนไขเริ่มรถ, เสียง, ข้อมูล Offline และ UART; Raspberry Pi 5 RAM 4GB ดูแลกล้อง, MPU6050, YOLO Segmentation และเป็น LTE/4G gateway เพียงตัวเดียว; Supabase Auth/PostgreSQL/Row Level Security (การกำหนดสิทธิ์เข้าถึงข้อมูลเป็นรายแถว) /Edge Functions/Realtime ดูแลบัญชีและ Session
C-002 [CONFIRMED] การเริ่ม Session ใหม่ทุกช่องทาง (Web/NFC) ต้องมีสิทธิ์อนุมัติออนไลน์ที่ตรวจสอบได้; เมื่อออนไลน์ไม่พร้อม ห้ามเริ่ม Session ใหม่; คำ Acknowledgment (ข้อความตอบกลับว่าได้รับคำสั่งหรือข้อมูลแล้ว) ของ UART ไม่ใช่หลักฐานว่ารถเริ่มทำงานจริง
C-003 [CONFIRMED; REVISED BY C-136–C-139] สิทธิ์ขอเริ่มรถถูกสงวนแบบ Atomic สูงสุด 5 นาที; รถหนึ่งคันมี Reservation/Active Session ได้ครั้งละหนึ่งราย; การเริ่มผ่านเว็บ/NFC ไม่ใช้สวิตช์ OFF→ON ต้องตรวจสิทธิ์เริ่มรถแยกจาก Approved และยืนยันความใกล้ก่อน Motor Ready
C-004 [CONFIRMED] ก่อนเริ่มต้องตรวจความนิ่ง คันเร่งเป็นศูนย์ BMS และเงื่อนไขบทบาท; ไม่เปิดมอเตอร์เองเมื่อกลับออนไลน์ และไม่ตัดกำลังรถที่กำลังวิ่งเพราะระบบเสริมขัดข้อง
C-005 [CONFIRMED; แก้ไข 15 ต.ค. 2569] Student/Employee ต้องมี AI พร้อมและ Main Geofence ที่ตั้งค่าแล้วเหมือนกัน; Manager มีข้อยกเว้น AI และ Main Geofence แต่ไม่ข้ามเงื่อนไขความปลอดภัยหลัก; Admin ไม่ใช่บัญชีขับรถ
C-006 [CONFIRMED] Pi รีสตาร์ตต้องประสาน Active Session เดิมกับ ESP32/Supabase ไม่สร้าง Session ใหม่เอง; กล้อง/AI คืนสู่สภาพพร้อมได้หลังตรวจสุขภาพและ Calibration; ข้อมูลเซนเซอร์หมดอายุต้องถูกปฏิเสธ
C-007 [CONFIRMED] การสื่อสาร ESP32↔Pi ใช้ UART framing แบบ COBS/0x00, CRC-32C, binary header 9 ไบต์ little-endian, max decoded 512 ไบต์, เริ่ม 115200 bps พร้อม Acknowledgment (ข้อความตอบกลับว่าได้รับคำสั่งหรือข้อมูลแล้ว)/retry bounded, idempotency และ fragmentation; ค่าระยะเวลาจริงและการทดสอบยัง PENDING TEST
C.2 การมองเห็นหน้าเว็บและบัญชี

C-010 [CONFIRMED] หน้า Landing Page ก่อนล็อกอินแสดงข้อมูลโครงการเท่านั้น; ไม่แสดงสถานะรถ ตำแหน่ง GPS หรือผู้ขับ; ผู้ใช้ต้องล็อกอินก่อนดูสถานะรถ
C-011 [CONFIRMED] Pending เข้าระบบเพื่อดูสถานะรถ คู่มือและข้อมูลโครงการได้ แต่ขอใช้รถผ่านเว็บ/NFC ไม่ได้ และไม่ดู Live GPS
C-012 [CONFIRMED] Rejected/Suspended เห็นเฉพาะข้อมูลบัญชี เหตุผลที่เปิดเผยได้ คู่มือ และปุ่มส่งคำขอทบทวน; ไม่เห็นสถานะรถ/Live GPS และไม่สามารถเริ่ม Session
C-013 [CONFIRMED] บัญชี Approved ดูสถานะรถตามสิทธิ์; เมื่อรถถูกใช้งานแสดงว่า 'รถกำลังถูกใช้งาน' และปิดคำขอ; ถ้า Blocked ผู้ใช้ทั่วไปเห็นเพียง 'รถไม่พร้อมให้บริการ' ไม่เห็นเหตุภายใน
C-014 [CONFIRMED] Login session คงอยู่จน Logout หรือ Auth session หมดอายุ/ถูกเพิกถอน; อนุญาตล็อกอินบัญชีเดียวกันหลายอุปกรณ์; Logout ออกจากเฉพาะอุปกรณ์ปัจจุบัน ไม่เพิ่ม UI ออกจากระบบทุกอุปกรณ์
C-015 [CONFIRMED] การมี Login session ไม่เท่ากับมีสิทธิ์เริ่มรถ; ต้องตรวจสิทธิ์ล่าสุดทุกครั้ง; Logout ระหว่างขับไม่ปิด Active Session หรือสั่งดับมอเตอร์
C-016 [CONFIRMED] หน้าเว็บไซต์เริ่มต้นภาษาไทยและรองรับภาษาอังกฤษ; คู่มือเปิดอ่านได้โดยสมัครใจ; Privacy Notice/ข้อตกลงการใช้รถก่อนเริ่มครั้งแรกยังเป็นขั้นตอนบังคับแยกต่างหาก
C-017 [CONFIRMED] บัญชีแก้เบอร์โทรศัพท์ตนเองได้; ชื่อ–นามสกุลแก้โดย Admin พร้อม Audit; อีเมลไม่ให้แก้ไขโดยทุกบทบาท; หากสูญเสียการเข้าถึงอีเมลต้องกู้ผ่านผู้ให้บริการอีเมล
C-018 [CONFIRMED] แสดงแบตเตอรี่ให้ผู้ขับเป็นป้ายสถานะ 'ปกติ/ต่ำ/กำลังชาร์จ/ไม่พร้อม' และเปอร์เซ็นต์แบตเตอรี่ ; ผู้ดูแลเห็นข้อมูลที่จำเป็น; AI แสดงเพียง 'พร้อมใช้งาน/ไม่พร้อมใช้งาน/กำลังตรวจสอบ'
C-019 [CONFIRMED; REVISED BY C-137–C-139] ผู้ใช้ส่งคำขอผ่าน Responsive Web App จากที่ใดก็ได้ แต่ Motor Ready จะอนุญาตได้ก็ต่อเมื่อยืนยันความใกล้รถและสิทธิ์ครบ; ไม่ใช้กุญแจหรือ OFF→ON เพิ่ม
C.3 การขอใช้รถ การยกเลิก การคืนรถ

C-020 [CONFIRMED] หน้า Reserved/Pending Start แสดงตัวนับถอยหลังเวลาคงเหลือจาก 5 นาทีและปุ่มยกเลิก; เวลาอ้างอิงจากระบบจริง ไม่ขยายจากการรีเฟรชหน้าเว็บ
C-021 [CONFIRMED] ผู้ใช้ยกเลิกคำขอที่ยังไม่เริ่ม Active ได้; นับและเก็บประวัติการยกเลิกซ้ำเพื่อจำกัดสิทธิ์ชั่วคราวเมื่อผิดปกติ; เกณฑ์/ระยะเวลารอกำหนดจาก Pilot; ใช้ข้อจำกัดทั้งเว็บและ NFC
C-022 [CONFIRMED] หากใช้สิทธิ์ชั่วคราว 5 นาทีซ้ำโดยไม่เริ่มรถ จนถึงเกณฑ์ ระบบจำกัดสิทธิ์ขอใหม่ชั่วคราว; แสดงเหตุผลและวันเวลาที่กลับมาใช้งานได้ พร้อมปิดปุ่มขอใช้รถ; ไม่เปลี่ยน Approved เป็น Suspended
C-023 [CONFIRMED] หาก Admin สั่งหยุดบริการหรือรถไม่พร้อมขณะมี Reservation 5 นาทีและยังไม่เริ่ม Active ให้ยกเลิกคำขอทันที แสดง 'รถไม่พร้อมให้บริการ' และไม่นับเป็นความผิดผู้ใช้หรือการยกเลิกซ้ำ
C-024 [CONFIRMED] รถหนึ่งคันมี Return Zone ของตัวเอง ตั้งโดย Admin แยกจาก Main Geofence; ผู้ใช้เห็นแผนที่ Return Zone และปุ่มเปิด Google Maps เพื่อนำทางกลับ
C-025 [CONFIRMED; REVISED BY C-141/C-143] จบ Session ปกติเมื่อเจ้าของสั่ง End ผ่านเว็บ/NFC รถหยุดนิ่งอย่างเชื่อถือได้ อยู่ใน Return Zone และยืนยัน Motor Ready ปิดจริง; หากเงื่อนไขไม่ครบห้าม Completed และห้ามผู้อื่นเริ่ม Session; คงข้อยกเว้นเดิมที่ต้องตรวจรถจริง
C-026 [CONFIRMED; REVISED BY C-142] ผู้ขับเดิมที่ Pause/Lock อยู่นอก Return Zone และต้องการกลับไปคืน สามารถขอ Resume ผ่านเว็บ/NFC โดยตรวจสิทธิ์ออนไลน์ ความใกล้รถ และความปลอดภัยใหม่ใน Session เดิม ไม่สร้าง Session ใหม่
C-027 [CONFIRMED; REVISED BY C-141/C-143] GPS รถไม่พร้อมในการตรวจคืนรถ อาจใช้ GPS โทรศัพท์ผู้ขับยืนยัน Return Zone ร่วมกับคำขอ End + การหยุดนิ่งที่เชื่อถือได้ + ผลยืนยัน Motor Ready ปิดจริง; หาก GPS รถที่เชื่อถือได้บอกว่าอยู่นอก Return Zone ให้ยึด GPS รถเหนือโทรศัพท์; การไม่ตรวจความใกล้ของโทรศัพท์กับตัวรถมีความเสี่ยง spoofing ที่ต้องบันทึก
C-028 [CONFIRMED; REVISED BY C-141/C-143; แก้ไข 15 ต.ค. 2569] เมื่อ Return Zone ไม่มี/ใช้ไม่ได้ Student/Employee เริ่มใหม่ไม่ได้; Manager อาจเริ่มได้หากเงื่อนไขอื่นผ่าน และปิด Session ตามข้อยกเว้นด้วยคำขอ End + หยุดนิ่ง + ยืนยัน Motor Ready ปิดจริงและบันทึกเหตุผล; เมื่อ Return Zone พร้อม ทุกบทบาทใช้เงื่อนไขกลับโซนตามปกติ
C-029 [CONFIRMED] Admin ปรับ Return Zone ได้เฉพาะรถจอด ไม่มี Active Session หรือ Pending End และบันทึกเหตุผล/การเปลี่ยนเวอร์ชัน; ผู้ใช้เห็นแผนที่พื้นที่ใช้งาน/Return Zone ก่อนเริ่มโดยไม่ต้องยืนยันการอ่าน
C-030 [CONFIRMED] กรณีรถเสียคืนไม่ได้ ผู้ขับแจ้งผ่านเว็บไซต์; Admin/Manager ต้องตรวจรถจริงก่อนปิด Session กรณีพิเศษ และบล็อก Session ใหม่จนรถปลอดภัย
C-031 [CONFIRMED] หลังคืนสำเร็จและผ่านเงื่อนไขความปลอดภัย หากไม่มี Block ให้รถเป็น AVAILABLE ได้ทันทีโดยไม่ต้องให้ผู้ดูแลอนุมัติทุกรอบ
C-032 [CONFIRMED] หน้าหลัง Completed แสดงสรุปวันเวลาเริ่ม–สิ้นสุด ระยะเวลารวม ระยะทาง (ระบุข้อมูลไม่ครบถ้วนแทน 0 หากขาดข้อมูล) และปุ่มกลับ Dashboard
C.4 หน้าผู้ขับ Dashboard และ My Trips

C-040 [CONFIRMED] ระหว่าง Active หน้าเว็บผู้ขับแสดงสถานะ Active Session, ระยะเวลาที่ผ่านไป, สถานะแบตเตอรี่แบบป้าย และสถานะ AI แบบป้าย; ไม่เพิ่มแผนที่สดในหน้าสรุประหว่างขับ แต่ยังเปิดดู Return Zone/Google Maps ผ่านเมนูเดิมได้
C-041 [CONFIRMED] เมื่อระบบไม่สามารถรับข้อมูลใหม่จากรถ ให้ซ่อนสถานะแบตเตอรี่/AI และขึ้นข้อความ 'ไม่สามารถรับข้อมูลจากรถได้' ไม่แสดงข้อมูลเก่าเป็นสด; Session ไม่ถูกสรุปว่าจบเพราะข้อมูลขาด
C-042 [CONFIRMED] Admin/Manager เห็นชื่อผู้ขับ บทบาท เวลาเริ่ม Session ตำแหน่ง GPS รถล่าสุดพร้อมเวลาอัปเดตระหว่าง Active; ผู้ใช้ทั่วไปไม่เห็นข้อมูลผู้ขับคนอื่น
C-043 [CONFIRMED] Admin/Manager มีปุ่มโทรไปยังเบอร์ผู้ขับปัจจุบันเฉพาะ Active Session (เปิดโทรศัพท์ปกติ ไม่ใช่ระบบคุยในแอป); ไม่เปิดเผยเบอร์ในประวัติหลังขับแก่ Manager
C-044 [CONFIRMED] My Trips ของผู้ขับแสดงวันที่ เวลาเริ่มและสิ้นสุด ระยะเวลา และระยะทาง เฉพาะประวัติของตนเอง; เรียงใหม่สุดก่อน; ไม่มีตัวกรองวันที่ ไม่มีเส้นทางย้อนหลัง/กราฟความเร็ว/ข้อมูล AI รายเหตุการณ์
C-045 [CONFIRMED] ผู้ใช้ลบหรือแก้ไข My Trips เองไม่ได้; เฉพาะ Admin แก้ข้อมูลเวลา/ระยะทางที่ผิดพลาดได้พร้อมเหตุผลและเก็บก่อน–หลังแก้/ผู้แก้/เวลาใน Audit Log(บันทึกการตรวจสอบ)
C-046 [CONFIRMED] เมื่อ Admin แก้ข้อมูล My Trips แล้ว หน้า My Trips แสดงค่าล่าสุดโดยไม่ต้องแจ้งผู้ใช้หรือแสดงเครื่องหมาย 'ถูกแก้ไข'; Audit Log(บันทึกการตรวจสอบ) ภายในยังต้องตรวจสอบได้
C-047 [CONFIRMED] ผู้ใช้กด 'รายงานข้อมูลผิดพลาด' บนรายการ My Trips พร้อมรายละเอียดส่งถึง Admin ผ่าน Dashboard เพื่อตรวจสอบ; ไม่มีสิทธิ์แก้เองและไม่ปรับข้อมูลอัตโนมัติ
C-048 [CONFIRMED — HISTORICAL; REVISED BY C-094] ประวัติ Session เก็บไว้ตลอดระยะเวลาโครงการ; เดิมยังไม่ได้กำหนดวิธีและระยะเวลาหลังสิ้นสุดโครงการ แต่ปัจจุบันให้ยึด C-094: ภายใน 30 วันหลังสิ้นสุดโครงการต้องลบหรือทำข้อมูลระบุตัวบุคคลให้ไม่สามารถเชื่อมโยงกลับได้ คงเฉพาะสถิติรวมที่ไม่ระบุตัวบุคคล โดยเคารพหน้าที่และข้อยกเว้นตามกฎหมาย
C.5 Dashboard แจ้งเตือน และเหตุขัดข้อง

C-050 [CONFIRMED] Admin/Manager ได้รับ Operational Alerts เฉพาะใน Dashboard ไม่ส่ง email/LINE/SMS/push; แสดงจำนวนยังไม่อ่าน และยังไม่อ่านจนผู้ดูแลกดรับทราบ
C-051 [CONFIRMED] อันดับการแจ้งเตือนเรียงระดับความสำคัญ โดยเรื่องความปลอดภัยขึ้นก่อน และทุกเหตุแสดงวันเวลาและสถานะรับทราบ
C-052 [CONFIRMED] มีแท็บ 'ยังไม่ได้รับทราบ' และ 'ทั้งหมด' ซึ่งแต่ละแท็บยังเรียงความสำคัญ; ยังไม่เพิ่มตัวกรองตามประเภท
C-053 [CONFIRMED] Admin หรือ Manager คนใดคนหนึ่งรับทราบการแจ้งเตือนแทนกันได้; บันทึกผู้รับทราบและเวลา; การรับทราบไม่ถือเป็นการแก้ไขเหตุหรือปลด Block
C-054 [CONFIRMED] ปัญหาเดิมที่เกิดต่อเนื่องให้รวมเป็น Alert Episode รายการเดียวพร้อมอัปเดตสถานะ; หากปัญหาสิ้นสุดแล้วกลับมาเกิดใหม่ ให้สร้างรายการใหม่; ยังเก็บรายการเหตุการณ์ต้นทางสำหรับ Audit
C-055 [CONFIRMED] เมื่อรถออฟไลน์ต่อเนื่องเกินระยะที่กำหนดจาก Pilot ให้แจ้ง Admin/Manager; หากกลับมาออนไลน์ให้เปลี่ยนสถานะเหตุการณ์เป็น 'กลับมาออนไลน์แล้ว' และเก็บประวัติ โดยยังถือว่ายังไม่รับทราบจนกดรับทราบ
C-056 [CONFIRMED] ผู้ใช้แจ้งปัญหารถผ่านเว็บด้วยหมวดและรายละเอียด; ปัญหาอันตรายสูง (เช่น เบรก/คันเร่ง) ต้องบล็อก Session ใหม่อัตโนมัติจนตรวจสอบความปลอดภัย; ไม่ดับเครื่องผู้ที่กำลังขับ
C-057 [CONFIRMED] ปัญหาไม่ร้ายแรงให้บันทึกและแจ้ง Admin/Manager แต่ไม่ Block อัตโนมัติ; Admin พิจารณาหยุดบริการด้วยตนเองได้
C-058 [CONFIRMED] เฉพาะ Admin เท่านั้นที่กดหยุด/เปิดให้บริการรถด้วยตนเอง (Manual OUT_OF_SERVICE); Manager ดู/รายงาน/ตรวจสอบได้ แต่ไม่กดสั่งเปลี่ยนสถานะ Manual OUT_OF_SERVICE; สิทธิ์ Manager ในตารางบทบาทเกี่ยวกับการจัดการ Safety Block ตามสิทธิ์และการตรวจรถ ไม่รวมอำนาจเปิด/หยุดให้บริการด้วยตนเองแบบ Manual OUT_OF_SERVICE (C-125/D-004)
C-059 [CONFIRMED] เมื่อ Admin สั่งหยุดบริการขณะ Active ให้แจ้งเตือนบนเว็บไซต์ผู้ขับและแนะนำให้จอดอย่างปลอดภัย; ไม่ดับเครื่อง/ไม่ปิด Session อัตโนมัติ; ผู้ขับต้องประเมินความปลอดภัย ถ้าปลอดภัยจึงกลับ Return Zone โดยการเปิดมอเตอร์ใหม่ต้องผ่านเงื่อนไขออนไลน์และข้อห้าม Block ที่มีผล หากไม่ปลอดภัยให้แจ้งผู้ดูแล
C-060 [CONFIRMED] การแจ้งการหยุดบริการผ่านเว็บไซต์อาจไม่ถูกเห็นขณะขับหรือออฟไลน์ จึงไม่ควรอ้างว่าเป็นระบบเตือนภัยที่รับประกันรับรู้ทันที
C-061 [CONFIRMED] มีเบอร์โทรกลางโครงการหนึ่งหมายเลข กำหนดโดย Admin; ปุ่มติดต่อเปิดแอปโทรศัพท์ ผู้ขับใช้ช่องทางเดิมยามฉุกเฉิน ไม่สร้าง SOS หรือ emergency messaging system ใหม่
C-062 [CONFIRMED] ผู้รายงานปัญหาเห็นเพียงการยืนยันว่าได้รับเรื่อง ไม่ต้องติดตามสถานะซ่อม; หลังจบ Session อาจเสนอช่องทางรายงานปัญหาโดยไม่บังคับ ไม่มีโมดูลประวัติซ่อมเฉพาะ
C.6 สถิติและรายงาน

C-070 [CONFIRMED] Admin/Manager มีหน้ารายงานสถิติการใช้งาน เลือกวันที่เพื่อดูวันต่อวัน ได้แก่ จำนวน Session, ระยะเวลารวม, ระยะเวลาเฉลี่ย, ระยะทางรวม, ระยะทางเฉลี่ย, จำนวนผู้ใช้ไม่ซ้ำ
C-071 [CONFIRMED] ไม่พัฒนาฟังก์ชันส่งออกรายงาน Excel/CSV/PDF; ดูได้เฉพาะบนเว็บไซต์
C-072 [CONFIRMED] ค่าเฉลี่ยและผลรวมที่พึ่งข้อมูลขาดหาย ต้องระบุความไม่สมบูรณ์ ไม่สมมติระยะทางที่หายไปเป็นศูนย์; ผู้ดูแลมีสิทธิ์ดูตาม Row Level Security (การกำหนดสิทธิ์เข้าถึงข้อมูลเป็นรายแถว)  ที่เหมาะสม
C.7 NFC การอนุมัติ และบทบาท

C-080 [CONFIRMED] บัญชี Approved ไม่จำเป็นต้องมี NFC; ขอใช้รถผ่านเว็บไซต์ได้; ต้องให้ Admin ลงทะเบียนบัตรก่อนจึงใช้ช่องทาง NFC ได้
C-081 [CONFIRMED] หนึ่งบัญชีใช้บัตร NFC ได้สูงสุดหนึ่งใบ; เมื่อ Admin ผูกบัตรใหม่ ให้ยกเลิกสิทธิ์บัตรเดิม; UID-only ยังคงมีความเสี่ยงถูกคัดลอกตามเอกสารฐาน
C-082 [CONFIRMED] ผู้ใช้สามารถเปิด/ปิดสิทธิ์บัตรที่ผูกบัญชีของตนผ่านเว็บไซต์ได้ โดยไม่เปิดสิทธิ์บัญชี Suspended/Rejected; การเปิด/ปิดบัตรไม่ตัดกำลังระหว่าง Active; Admin เท่านั้นลงทะเบียนบัตรใหม่
C-083 [CONFIRMED] Admin ตรวจสอบและอนุมัติ Pending ทีละบัญชีเท่านั้น (ไม่มี Bulk Approval); ต้องตรวจความเกี่ยวข้องกับมหาวิทยาลัยและกำหนดบทบาทให้ถูกต้อง
C-084 [CONFIRMED] Admin ตรวจสถานะนักศึกษา/บุคลากรด้วยตนเองนอกระบบ ไม่มีระบบอัปโหลดเอกสารหลักฐานยืนยันสถานะ; ผู้ใช้ Pending ดูสถานะรถ/คู่มือ/ข้อมูลโครงการ แต่ไม่มีสิทธิ์ใช้รถ
C-085 [CONFIRMED] เมื่อ Admin พบว่าผู้ใช้ไม่มีคุณสมบัติ สามารถตรวจสอบและระงับบัญชีได้โดยไม่ต้องตรวจเป็นรอบ; ผู้ใช้เห็นเหตุผลและส่งคำขอทบทวนผ่านเว็บได้
C-086 [CONFIRMED] เฉพาะ Admin เปลี่ยนบทบาทผู้ใช้; ไม่เพิ่มระบบขอเปลี่ยนบทบาท; ไม่แจ้งผู้ใช้เมื่อบทบาทเปลี่ยน แต่โปรไฟล์แสดงบทบาทล่าสุด; Audit ต้องบันทึกก่อน–หลัง/ผู้ทำ/เหตุผล/เวลา
C-087 [CONFIRMED] หน้า Admin User Management ค้นหาจากชื่อหรืออีเมล และกรอง Pending/Approved/Rejected/Suspended ได้; ไม่มี Bulk Approval
C-088 [CONFIRMED] เมื่อ Admin อนุมัติหรือปฏิเสธบัญชี แสดงผลในเว็บไซต์เท่านั้น พร้อมเหตุผลกรณีถูกปฏิเสธ ไม่ส่ง Email/LINE/SMS/Push
C-089 [CONFIRMED] การจำกัดสิทธิ์อัตโนมัติเนื่องจาก no-show/cancellation ซ้ำใช้กับ NFC และเว็บ แต่ไม่ให้สับสนกับบัญชี Suspended ซึ่งต้องจัดการตามสิทธิ์
C.8 ปิดบัญชีและข้อมูลส่วนบุคคล

C-090 [CONFIRMED] ผู้ใช้ปิดใช้งานบัญชีตนเองผ่านเว็บได้ แต่ไม่ใช่คำสั่งลบข้อมูลถาวร; การขอลบข้อมูลถาวรต้องเป็นกระบวนการแยกตามนโยบายและกฎหมาย
C-091 [CONFIRMED] ปิดบัญชีได้เมื่อไม่มี Reservation/Pending Start/Active/Pending End หรือธุรกรรม Session ค้างอยู่; หากมีคำขอชั่วคราว ให้จัดการ/ยกเลิกให้เรียบร้อยก่อน ไม่ปิดพร้อมยกเลิกอัตโนมัติ; หากขับอยู่ต้องคืนให้ Completed ก่อน
C-092 [CONFIRMED] บัญชีปิดแล้วไม่เปิดกลับมา; ผู้ใช้ต้องสมัครใหม่ ยืนยันอีเมลและรอ Admin อนุมัติใหม่; อีเมลเดิมใช้สมัครบัญชีใหม่ได้เมื่อดำเนินการจัดการข้อมูล Auth เดิมถูกต้องแล้ว

2. มติล่าสุดที่ CONFIRMED ชนะข้อขัดแย้งกับเอกสารฐาน เฉพาะหัวข้อนั้น ๆ; หากมีความขัดแย้งใหม่ ให้ระบุอย่างชัดเจน ไม่เดาว่าฝ่ายใดถูก

ภาคผนวก D — มติภาพรวมโครงการที่ยืนยันเพิ่มเติม (14 ต.ค. 2569)

ภาคผนวกนี้บันทึกมติที่ผู้จัดทำโครงการยืนยันต่อจากภาคผนวก C ใช้เป็น Requirements Working Baseline (ฐานข้อกำหนดที่ใช้ดำเนินงานต่อ) แต่ไม่ใช่หลักฐานว่าติดตั้งระบบหรือทดสอบรถสำเร็จแล้ว
D.0 ลำดับความสำคัญของข้อกำหนดและคำศัพท์

มติ CONFIRMED ในภาคผนวก D และข้อ C ที่แก้ไขใหม่มีผลเหนือข้อความเดิมในหัวข้อที่ขัดกันเท่านั้น; หากมติหนึ่งยังเป็น PENDING (รอการตัดสินใจ) ห้ามถือว่าได้อนุมัติแล้ว โดยต้องรักษาข้อกำหนดด้านความปลอดภัยและสิทธิ์ของแต่ละบทบาทตามเดิม
• Pilot Test (การทดลองประเมินระบบต้นแบบภายใต้แผนและเกณฑ์วัดผล)
• Real Riding Test (การทดลองขับรถจริงในพื้นที่ที่ได้รับอนุญาต)
• Bench Test (การทดสอบบนแท่นทดสอบ ซึ่งโครงการเลือกไม่ดำเนินการ)
• Acceptance Criteria (เกณฑ์ตรวจรับที่ต้องมีหลักฐานพิสูจน์ก่อนสรุปว่าผ่าน)
• Safety Block (สถานะระงับการเริ่ม Session ใหม่ด้วยเหตุด้านความปลอดภัย)
• Manual OUT_OF_SERVICE (สถานะหยุดให้บริการรถที่ Admin สั่งด้วยตนเอง)
• Privacy Notice (ประกาศแจ้งวัตถุประสงค์และวิธีประมวลผลข้อมูลส่วนบุคคล)
• Data Subject Request (คำขอใช้สิทธิข้อมูลส่วนบุคคล เช่น เข้าถึง แก้ไข หรือลบข้อมูล)
• De-identification (การลบหรือเปลี่ยนข้อมูลจนไม่สามารถระบุตัวบุคคลหรือเชื่อมกลับได้ตามเป้าหมาย)
• GPS Fix (ผลระบุตำแหน่งจากเครื่องรับ GPS ที่ต้องตรวจความสดใหม่และความน่าเชื่อถือ)
• Web Speech (ระบบเสียงพูดหรือเสียงแจ้งเตือนผ่านเว็บไซต์ ซึ่งไม่พัฒนาในโครงการนี้)
• Integration Test (การทดสอบว่าองค์ประกอบที่พัฒนาแยกกันทำงานร่วมกันได้ถูกต้อง)
D.1 นโยบายผู้ใช้และสิทธิ์การเริ่ม Session

D-001 [CONFIRMED; อ้างอิง C-116] GPS รถไม่พร้อมหรือไม่เชื่อถือได้ก่อนเริ่ม Session ใหม่: ห้าม Student (นักศึกษา) และ Employee (บุคลากร); Manager อนุญาตได้เฉพาะเมื่อออนไลน์และผ่านเงื่อนไขความปลอดภัยอื่นทั้งหมด; Admin (ผู้ดูแลระบบ) ไม่ใช่บัญชีสำหรับขับรถ. ไม่ใช้ GPS โทรศัพท์แทนสำหรับการเริ่ม Session ตามมตินี้
D-002 [CONFIRMED; อ้างอิง C-117] ผู้โดยสารซ้อนท้ายเป็น OUT OF SCOPE (นอกขอบเขตโครงการ) ในการพัฒนารอบนี้ ไม่ตีความเป็นการอนุญาตหรือห้ามทางกฎหมาย; คุณสมบัติและใบอนุญาตผู้ขับให้ทีมโครงการตรวจสอบนอกระบบเว็บไซต์ก่อนอนุญาตให้ขับ
D-003 [CONFIRMED; แก้ไข 15 ต.ค. 2569; อ้างอิง C-110] Admin สามารถกำหนดและเปลี่ยนวัน/เวลาเริ่ม Session ของ Student/Employee ได้ตลอดเวลาผ่านเว็บไซต์ โดยไม่กำหนดชั่วโมงเริ่มต้นตายตัว; Manager ไม่ถูกจำกัดด้วยช่วงนี้ และไม่ดับเครื่องเมื่อ Active Session ที่เริ่มถูกต้องเลยช่วงเวลา
D-004 [CONFIRMED; อ้างอิง C-125] หากมีทั้ง Safety Block และ Manual OUT_OF_SERVICE ต้องปลดแต่ละสถานะตามสิทธิ์และตรวจความปลอดภัยครบก่อน จากนั้น Admin ต้องกดยืนยันเปิดให้บริการขั้นสุดท้ายอีกครั้งก่อนรถเป็น AVAILABLE; Manager ไม่สามารถสั่งยกเลิก Manual OUT_OF_SERVICE ของ Admin ได้
D.2 นโยบายเว็บไซต์และการจัดการข้อมูล

D-005 [CONFIRMED; อ้างอิง C-094] ประวัติ Session ระหว่างดำเนินโครงการเก็บตามข้อกำหนดเดิม; หลังสิ้นสุดโครงการดำเนินการลบหรือทำให้ไม่สามารถระบุตัวบุคคล/เชื่อมโยงกลับได้ภายใน 30 วัน เหลือเพียงสถิติรวมที่ไม่ระบุตัวบุคคลเพื่อการศึกษา ทั้งนี้ไม่ละเมิดหน้าที่หรือข้อยกเว้นที่กฎหมายกำหนด
D-006 [CONFIRMED; อ้างอิง C-094] เพิ่มแบบฟอร์ม Data Subject Request (คำขอใช้สิทธิข้อมูลส่วนบุคคล) บนเว็บไซต์แยกจากปุ่มปิดบัญชี เพื่อยื่นคำขอเข้าถึง/แก้ไข/ลบข้อมูลและส่งต่อ Admin ตรวจสอบตัวตนและพิจารณา; ไม่อนุมัติลบทุกคำขออัตโนมัติ
D-007 [CONFIRMED] เว็บไซต์ไม่มี Web Speech (เสียงพูดหรือเสียงแจ้งเตือนจากเว็บไซต์); แสดงเพียงข้อความและสถานะ ส่วนเสียงแจ้งเตือนภาษาไทยบนตัวรถจาก ESP32-S3 ยังคงใช้ตามข้อกำหนดเดิม
D-008 [CONFIRMED] ทีมพัฒนาทั้ง 4 คนจัดทำ Privacy Notice (ประกาศแจ้งการประมวลผลข้อมูลส่วนบุคคล) และข้อตกลงการใช้รถ ให้อาจารย์ที่ปรึกษาตรวจทานก่อนเผยแพร่ โดยผู้ใช้ต้องรับทราบตามข้อกำหนดเดิมก่อนใช้รถครั้งแรก
D.3 แผนการทดลองและการยอมรับผล Pilot Test

D-009 [CONFIRMED] ใช้ Real Riding Test (การทดลองขับจริง) เท่านั้น ไม่ดำเนิน Bench Test (การทดสอบบนแท่น); สถานที่เป็นพื้นที่ปิดหรือพื้นที่ควบคุมภายในมหาวิทยาลัยวลัยลักษณ์ที่ไม่มีการจราจรทั่วไปและได้รับอนุญาต ไม่ใช่การเปิดให้ขับบนถนนสาธารณะ
D-010 [CONFIRMED] ก่อนทดลองขับจริงต้องตรวจความพร้อมและความปลอดภัยรถ/ระบบที่จำเป็น โดยเฉพาะเบรก คันเร่ง วงจรมอเตอร์ BMS และอุปกรณ์เสริม; สมาชิกทีมพัฒนา 4 คนกับอาจารย์ที่ปรึกษาร่วมพิจารณาความพร้อมและอนุมัติระดับโครงการ พร้อมได้รับอนุญาตใช้พื้นที่ตามระเบียบ หากเงื่อนไขความปลอดภัยพิสูจน์ไม่ได้ ห้ามเริ่มทดลองขับ
D-011 [CONFIRMED] ผู้มีสิทธิ์เข้าร่วมทดลองขับคือสมาชิกทีมพัฒนาและอาจารย์ที่ปรึกษาที่ผ่านการตรวจคุณสมบัติผู้ขับตามข้อกฎหมาย/ระเบียบแล้ว ไม่ถือว่าทุกคนต้องขับจริง; ทีมโครงการเป็นผู้ตรวจคุณสมบัตินอกเว็บไซต์
D-012 [CONFIRMED] ทดลองขับอย่างน้อย 10 รอบตามเกณฑ์ใน Word และมีข้อมูลเพียงพอต่อการประเมิน; ไม่กำหนดจำนวนวันตายตัว ไม่ลดขั้นตอนความปลอดภัยเพื่อเร่งให้ครบจำนวนรอบ
D-013 [CONFIRMED] ระหว่าง Pilot Test หากพบปัญหาเสี่ยงอันตราย ให้ผู้ขับจอดอย่างปลอดภัยและหยุด Pilot ทั้งหมดทันทีโดยไม่สั่งตัดกำลังมอเตอร์กะทันหัน; ทีมและอาจารย์ตรวจสอบ/แก้ไขและพิจารณาความพร้อมก่อนเริ่มใหม่. ปัญหาที่ไม่กระทบความปลอดภัยให้บันทึกและตรวจสอบ แล้วพิจารณาทดลองต่อได้
D-014 [CONFIRMED] เมื่อผล Pilot Test ไม่ผ่าน Acceptance Criteria (เกณฑ์ตรวจรับ) ที่กำหนด ต้องแก้ไขและทดลองซ้ำจนทุกเกณฑ์ผ่านจริง จึงสรุปว่าพัฒนาสำเร็จ; ห้ามรับรองผลที่ไม่ผ่านจริง และห้ามทดลอง/ใช้งานต่อเมื่อยังมีความเสี่ยงด้านความปลอดภัย
D-015 [CONFIRMED] เมื่อผลทดลองเสร็จสิ้น ให้สมาชิกทีมพัฒนาทั้ง 4 คนและอาจารย์ที่ปรึกษาร่วมตรวจสอบหลักฐานและรับรองรายงานผล Pilot Test ก่อนสรุปและส่งมอบ; การรับรองเอกสารต้องไม่แทนผลทดสอบจริง
D.4 รูปแบบการแบ่งงานและประเด็นที่ยังเปิดอยู่

D-016 [CONFIRMED] ทีมพัฒนา 4 คนแบ่งเป็น 2 คู่ร่วมรับผิดชอบงาน: คู่ที่ 1 ดูแล Web และ Cloud; คู่ที่ 2 ดูแล ESP32 และ Raspberry Pi/AI; ทุกคนร่วม Integration Test และจัดทำหลักฐานการพัฒนา ยังไม่มีการระบุชื่อสมาชิกแต่ละคู่
D-017 [CONFIRMED POLICY / PENDING DESIGN & TEST; อ้างอิง C-124] เก็บพิกัดจริงจาก GPS โทรศัพท์สำหรับตรวจ Return Zone ทั้งกรณีผ่านและไม่ผ่านเป็นเวลา 30 วันหลังการตรวจแต่ละครั้ง แล้วลบพิกัดดิบโดยอัตโนมัติ คงผลการตรวจและเวลาตาม Session history; สิทธิ์เข้าถึงและขั้นตอนสอบสวน spoofing ดูภาคผนวก F; ยังต้องทดสอบความน่าเชื่อถือและปฏิบัติตาม C-094/กฎหมายข้อมูลส่วนบุคคล
D-018 [PENDING TEST/DESIGN] รายละเอียดวิธีทดสอบค่าทางเทคนิค ความปลอดภัยของวงจร E-lock/Enable ความน่าเชื่อถือ GPS/IMU และ State Transition ของการเปิดให้บริการหลังปลดระงับยังต้องออกแบบ/ตรวจวัดจริง; มติระดับภาพรวมไม่ใช่ผลการทดสอบผ่าน
D.5 รายการตรวจสอบเพื่อส่งต่องาน

☐ ปรับ Use Case (กรณีการใช้งาน), State Diagram (แผนภาพสถานะ) และ Test Case (กรณีทดสอบ) ให้ครอบคลุมสิทธิ์ GPS ของ 4 บทบาท, เวลาที่ Admin เปลี่ยนได้, แบบฟอร์มข้อมูลส่วนบุคคล, และการยืนยันเปิดบริการขั้นสุดท้าย
☐ ยืนยันขอบเขต Real Riding Test ในพื้นที่ปิดที่ได้รับอนุญาต โดยตรวจความปลอดภัยก่อนขับทุกครั้ง และรายงานผลอย่างน้อย 10 รอบโดยไม่จำกัดจำนวนวัน
☐ จัดทำ Privacy Notice/ข้อตกลงการใช้รถและแบบฟอร์มคำขอใช้สิทธิข้อมูลส่วนบุคคล พร้อมกระบวนการพิจารณาของ Admin และการตรวจทานโดยอาจารย์
☐ กำหนดชื่อผู้รับผิดชอบของแต่ละคู่เมื่อทีมพร้อม และจัดเก็บหลักฐาน Integration Test/ผล Pilot และการรับรองร่วมกัน
☑ นโยบายจัดเก็บพิกัด GPS โทรศัพท์ของ C-124 ยืนยันแล้วตามภาคผนวก F (30 วันนับจากแต่ละการตรวจและลบพิกัดดิบอัตโนมัติ); ☐ ยังต้องออกแบบและทดสอบ GPS spoofing/ความน่าเชื่อถือ และกำหนดเกณฑ์ Pilot ของ C-123

## ภาคผนวก E — มติ C-123 ที่ยืนยันเพิ่มเติม (ข้อ 25–69; 14 ต.ค. 2569)

**สถานะ:** CONFIRMED POLICY THROUGH Q69; ค่าเกณฑ์/หน้าต่างประเมิน/ช่วงคูลดาวน์และ Dashboard Alert ของรถออฟไลน์ยัง PENDING TEST

ภาคผนวกนี้ใช้แทนข้อความเดิมเฉพาะส่วนที่ขัดแย้ง โดยยังรักษาข้อกำหนดเดิม C-023, C-056, C-094 และกฎความปลอดภัยทั้งหมด

### E.1 การประเมิน Cancellation / No-show และคำเตือน (ข้อ 25–31)

- **C-123/Q25 [CONFIRMED]:** แยกตัวนับ Cancellation (ผู้ใช้ยกเลิก Reservation เอง) กับ No-show (Reservation 5 นาทีหมดอายุโดยไม่ได้เริ่ม Session) โดยไม่รวมกันเพื่อตัดสินข้อจำกัดชั่วคราว; การยกเลิกเพราะ Admin/ระบบทำให้รถไม่พร้อมตาม C-023 ไม่นับเป็นความผิดผู้ใช้
- **C-123/Q26 [CONFIRMED]:** ข้อจำกัดเริ่ม Session ใหม่จาก Cancellation หรือ No-show ซ้ำหมดอายุอัตโนมัติเมื่อถึงเวลาที่กำหนด ไม่ต้องขอ Admin อนุมัติ; การหมดอายุไม่ได้รับประกันว่าจะเริ่ม Session ได้ ต้องตรวจเงื่อนไขบัญชี รถ Session ออนไลน์ และความปลอดภัยทั้งหมดอีกครั้ง
- **C-123/Q27 [CONFIRMED; CLARIFIED BY Q66]:** เมื่อข้อจำกัดประเภทหนึ่งหมดอายุ ให้รีเซ็ตเฉพาะตัวนับของประเภทนั้นตาม Q66; อีกประเภทไม่รีเซ็ตเพราะข้อจำกัดต่างประเภทหมดอายุ ประวัติเหตุการณ์ยังคงอยู่
- **C-123/Q28 [CONFIRMED]:** เมื่อ Cancellation หรือ No-show ใกล้ถึงเกณฑ์จำกัดสิทธิ์ที่กำหนดจาก Pilot Test เว็บไซต์ต้องเตือนผู้ใช้ล่วงหน้า
- **C-123/Q29 [CONFIRMED]:** คำเตือนต้องระบุว่าเป็น Cancellation หรือ No-show พร้อมจำนวนเหตุการณ์ชนิดนั้นที่ยังเกิดเพิ่มได้ก่อนถึงเกณฑ์จำกัดสิทธิ์ ห้ามนำตัวนับสองชนิดมารวมกัน
- **C-123/Q30 [CONFIRMED]:** แสดงคำเตือนทันทีเมื่อถึงระดับเตือน และคงไว้บน Dashboard ตราบที่ตัวนับยังอยู่ในช่วงเตือน; นำออกเมื่อไม่เข้าเงื่อนไขเตือนหรือมีการรีเซ็ตตัวนับ
- **C-123/Q31 [CONFIRMED]:** ถ้าตัวนับ Cancellation และ No-show ต่างเข้าเกณฑ์ใกล้จำกัดสิทธิ์พร้อมกัน ให้แสดงคำเตือนสองรายการแยกจากกัน พร้อมจำนวนครั้งที่เหลือของแต่ละประเภท

### E.2 กรณีผิดพลาดทางเทคนิคและการปลดข้อจำกัด (ข้อ 32–37)

- **C-123/Q32 [CONFIRMED]:** Reservation 5 นาทีที่หมดอายุเพราะรถหรือระบบขัดข้องจริง เช่น NFC/4G ห้ามนับเป็น No-show ที่เป็นความผิดผู้ใช้เมื่อพิสูจน์ได้; คงบันทึกเหตุขัดข้องและสาเหตุ
- **C-123/Q33 [CONFIRMED]:** Admin หรือ Manager ตรวจหลักฐาน ยืนยันการยกเว้นเหตุขัดข้อง และแก้ตัวนับ No-show ที่เคยนับไปแล้วได้ โดยต้องบันทึกผู้รับผิดชอบ เหตุผล/หลักฐาน และเวลาใน Audit Log
- **C-123/Q34 [CONFIRMED]:** หากตรวจยืนยันเหตุขัดข้องและแก้ No-show ของรอบประเมินที่เกี่ยวข้องจนต่ำกว่าเกณฑ์จำกัดสิทธิ์ ให้ระบบปลดเฉพาะข้อจำกัด No-show โดยอัตโนมัติทันทีและบันทึกเหตุการณ์; ไม่ปลด Cancellation, GPS-spoofing, Suspended, Safety Block หรือเงื่อนไขอื่น

- **C-123/Q37 [CONFIRMED]:** เก็บแจ้งเตือนข้อ 35–36 ในประวัติที่ผู้ใช้มองเห็น 30 วันนับจากเวลาสร้างแจ้งเตือนแต่ละรายการ จากนั้นนำออกอัตโนมัติ; Audit Log การแก้ไข/ปลดข้อจำกัดเก็บตามนโยบาย Audit Log เดิม

### E.3 การร้องขอทบทวนและการตรวจสอบ (ข้อ 38–46)

- **C-123/Q38 [CONFIRMED]:** ผู้ใช้ขอทบทวน No-show ที่น่าจะเกิดจากระบบ/รถขัดข้องได้ทั้งระบบแจ้งปัญหาเว็บไซต์ C-056 และเบอร์โทรกลางโครงการ ไม่ต้องสร้างระบบร้องเรียนใหม่; Admin/Manager เป็นผู้ตรวจหลักฐานและแก้ไขตามสิทธิ์

- **C-123/Q42 [CONFIRMED]:** หาก Reservation 5 นาทีหมดอายุและเพียงสงสัยว่า NFC/4G หรือระบบขัดข้อง แต่ยังไม่พิสูจน์ ให้ยังนับ No-show ชั่วคราวต่อการประเมินและข้อจำกัดตามปกติ; หาก Admin/Manager ยืนยันความผิดพลาดในภายหลัง จึงยกเว้น/แก้ไขตามข้อ 32–34

- **C-123/Q44 [CONFIRMED]:** ถ้าตรวจสอบเบื้องต้นเสร็จแต่หลักฐานไม่เพียงพอยืนยันว่าระบบขัดข้อง ให้เปลี่ยนสถานะเป็น «ตรวจสอบเสร็จสิ้น — ไม่พบหลักฐานยืนยันระบบขัดข้อง» คงตัวนับเดิม บันทึกเหตุผล ผู้ตรวจสอบ และเวลาตัดสิน พร้อมแจ้งผลทางเว็บไซต์; ต่างจากการปฏิเสธคำขอจากผู้ใช้ตามข้อ 39
- **C-123/Q45 [CONFIRMED]:** เก็บแจ้งผลเว็บไซต์ของข้อ 44 ไว้ในประวัติที่เจ้าของบัญชีมองเห็นตลอดอายุโครงการ; เมื่อสิ้นสุดโครงการจัดการข้อมูลส่วนบุคคลตาม C-094
- **C-123/Q46 [CONFIRMED]:** แจ้งผลของข้อ 44–45 ไม่ต้องกด «รับทราบ» ระบบลงประวัติทันทีตลอดโครงการ และการรับทราบ/ไม่รับทราบไม่เป็นเงื่อนไขเริ่ม Session

### E.4 การเปิดตรวจสอบใหม่และการแจ้งเตือน (ข้อ 47–53)

- **C-123/Q47 [CONFIRMED]:** เมื่อพบหลักฐานใหม่หลังปิดผลตรวจสอบเบื้องต้นว่าไม่พบหลักฐานระบบขัดข้อง ให้เปิดตรวจสอบเหตุการณ์เดิมใหม่ได้ ทั้งจากคำขอผู้ใช้ผ่าน C-056/เบอร์กลาง และหลักฐานที่ Admin/Manager พบเอง โดยเก็บผล/ประวัติเดิม; เมื่อพิสูจน์ว่าขัดข้องให้แก้ No-show และใช้กฎปลดข้อจำกัดตามกรณี
- **C-123/Q48 [CONFIRMED]:** ทุกครั้งที่เปิดตรวจสอบใหม่ตามข้อ 47 ให้สร้างแจ้งเตือนเว็บไซต์ใหม่และเปลี่ยนสถานะเหตุการณ์เป็น «เปิดตรวจสอบใหม่ — อยู่ระหว่างตรวจสอบหลักฐานเพิ่มเติม» โดยคงผลและประวัติเดิม รวมถึงตัวนับ/ข้อจำกัดปัจจุบันระหว่างรอหลักฐานยืนยัน
- **C-123/Q49 [CONFIRMED]:** เก็บแจ้งเตือนการเปิดตรวจสอบใหม่ตามข้อ 48 ในประวัติที่ผู้ใช้มองเห็นตลอดอายุโครงการ; จัดการข้อมูลส่วนบุคคลตาม C-094 หลังสิ้นสุดโครงการ
- **C-123/Q50 [CONFIRMED]:** แจ้งเตือนข้อ 48–49 ไม่ต้องกด «รับทราบ» และลงประวัติทันที; ตัวแจ้งเตือนและการอ่านไม่ใช่เงื่อนไขเริ่ม Session
- **C-123/Q51 [CONFIRMED]:** ถ้า Admin/Manager ยืนยันระบบ/รถขัดข้องและแก้ไข No-show สำเร็จ แม้ไม่มีข้อจำกัด No-show ที่ต้องปลด ให้เปลี่ยนสถานะเหตุการณ์เป็นแก้ไขแล้ว และแจ้งผู้ใช้ผ่านเว็บไซต์พร้อมเหตุผลและวันเวลา โดยไม่แสดงเท็จว่าได้ปลดข้อจำกัด
- **C-123/Q52 [CONFIRMED]:** แจ้งเตือนการแก้ไขตามข้อ 51 ไม่ต้องกด «รับทราบ»; แสดงและลงประวัติทันที และไม่ใช้การอ่านหรือรับทราบเป็นเงื่อนไขเริ่ม Session
- **C-123/Q53 [CONFIRMED]:** เก็บแจ้งเตือนข้อ 51–52 ในประวัติที่ผู้ใช้มองเห็น 30 วันนับจากเวลาสร้างแต่ละรายการ แล้วนำออกอัตโนมัติ; คง Audit Log ตามนโยบายเดิม

### E.5 กำหนดเวลาคำขอทบทวนและอำนาจเจ้าหน้าที่ (ข้อ 54–56)

- **C-123/Q54 [CONFIRMED]:** คำขอทบทวน No-show ครั้งแรกที่ผู้ใช้เป็นผู้ยื่นต้องยื่นภายใน 30 วันนับจากเวลาเหตุการณ์ No-show ผ่าน C-056 หรือเบอร์กลาง; วิธีพิจารณาและ Audit Log ตามข้อเดิม
- **C-123/Q55 [CONFIRMED]:** ถ้าคำขอทบทวนครั้งแรกยื่นภายใน 30 วันแล้ว ผู้ใช้สามารถขอทบทวนเหตุการณ์เดิมซ้ำหลังครบ 30 วันได้ตลอดโครงการเมื่อมีหลักฐานใหม่ โดยคงประวัติเดิม; แต่ผู้ใช้ไม่มีสิทธิ์ยื่นคำขอครั้งแรกผ่านช่องทางปกติหลังเส้นตาย
- **C-123/Q56 [CONFIRMED]:** Admin หรือ Manager ที่ค้นพบหลักฐานระบบขัดข้องใหม่เองสามารถเปิดตรวจสอบ No-show ย้อนหลังได้ตลอดโครงการ แม้เกิน 30 วันและผู้ใช้ไม่เคยยื่นคำขอแรกทันกำหนด; เก็บหลักฐาน/ประวัติ/Audit Log และแก้ไขหากพิสูจน์ได้ ข้อนี้ไม่ขยายสิทธิ์ผู้ใช้ให้ยื่นคำขอครั้งแรกหลัง 30 วัน

### E.6 การแก้ไขข้ามรอบประเมินและการคงข้อจำกัด (ข้อ 57–60)

- **C-123/Q57 [CONFIRMED]:** หากพบภายหลังว่า No-show ในรอบประเมินเก่าที่ปิด/รีเซ็ตแล้วเกิดจากระบบขัดข้องจริง ต้องแก้สถานะ/ผลประเมินเหตุการณ์ย้อนหลัง; Admin/Manager พิจารณาเป็นรายกรณีว่าจะลดตัวนับ No-show รอบปัจจุบันด้วยหรือไม่ และบันทึกเหตุผล ผู้ตัดสิน การดำเนินการ และเวลาใน Audit Log
- **C-123/Q58 [CONFIRMED]:** ถ้า Admin/Manager อนุมัติชดเชย No-show รอบเก่าเพื่อลดตัวนับรอบปัจจุบันจนต่ำกว่าเกณฑ์ ข้อจำกัด No-show ปัจจุบันที่ยังมีผลอยู่จะไม่ถูกปลดอัตโนมัติ ต้องมี Admin หรือ Manager อนุมัติการปลดแยก และบันทึกใน Audit Log; ข้อจำกัดยังมีผลจนกว่าอนุมัติหรือหมดอายุตามปกติ ข้อนี้ต่างจากข้อ 34
- **C-123/Q59 [CONFIRMED]:** ชดเชยจากรอบเก่าเพื่อลดตัวนับ No-show รอบปัจจุบันได้ต่ำสุด 0 เท่านั้น ห้ามติดลบ และห้ามยกยอดชดเชยส่วนเกินไปใช้ในรอบถัดไป; Audit Log ต้องบันทึกจำนวนที่ลดจริง ผู้ดำเนินการ เหตุผล และเวลา
- **C-123/Q60 [CONFIRMED]:** เมื่อปรับตัวนับรอบปัจจุบันลงต่ำกว่าเกณฑ์จากการชดเชยรอบเก่า แต่ยังรออนุมัติปลดข้อจำกัดแยก เว็บไซต์ต้องแสดงตัวนับล่าสุดและสถานะ «ปรับปรุงตัวนับแล้ว — รออนุมัติปลดข้อจำกัด» พร้อมชี้แจงว่าข้อจำกัด No-show ยังมีผล จนอนุมัติปลดหรือหมดอายุตามปกติ และการเปลี่ยนสถานะแสดงผลไม่ใช่การปลดข้อจำกัด

### E.7 ข้อย้ำความแตกต่างสำคัญ

- **แก้ No-show รอบปัจจุบัน (Q34):** หากพิสูจน์ระบบขัดข้องและแก้ตัวนับต่ำกว่าเกณฑ์ ระบบปลดเฉพาะ No-show restriction อัตโนมัติ
- **ชดเชยผิดพลาดข้ามรอบ (Q57–60):** ถ้าลดตัวนับรอบปัจจุบันจากการชดเชยรอบเก่า ข้อจำกัด No-show ที่ยังมีผลต้องได้รับการอนุมัติปลดแยกจาก Admin/Manager แม้ต่ำกว่าเกณฑ์
- **แจ้งเตือน C-123 ที่แสดง 30 วันหลังสร้าง:** ปลดข้อจำกัดสำเร็จ (Q37) และแก้ No-show สำเร็จโดยไม่มีข้อจำกัดให้ปลด (Q53)
- **แจ้งเตือน C-123 ที่แสดงตลอดโครงการ:** ตรวจสอบไม่พบหลักฐานยืนยันระบบขัดข้อง (Q45) และเปิดตรวจสอบซ้ำ (Q49)
- **การรับทราบ:** แจ้งเตือน C-123 ประเภทที่ระบุใน Q36, Q46, Q50, Q52 ไม่บังคับกดรับทราบ ซึ่งต่างจากแจ้งเตือนการแก้สรุปคำชี้แจง GPS ตาม C-124

- **C-123/Q67 [CONFIRMED; A]:** Admin สามารถปรับเกณฑ์จำนวนครั้งที่ก่อให้เกิดข้อจำกัด Cancellation/No-show และระยะเวลา Cooldown ผ่านเว็บไซต์ได้; ค่าตั้งต้นเชิงตัวเลขยังต้องมาจาก Pilot Test
- **C-123/Q68 [CONFIRMED; A]:** เกณฑ์และระยะเวลา Cooldown ใหม่ที่ Admin เปลี่ยนให้ใช้เฉพาะการประเมินหลังเวลาที่เปลี่ยน ไม่ย้อนหลังและไม่เปลี่ยนข้อจำกัดที่เริ่มก่อนหน้านั้น
- **C-123/Q69 [CONFIRMED; B]:** Dashboard แสดงเฉพาะคำเตือนเมื่อ Cancellation หรือ No-show ใกล้ถึงเกณฑ์ แยกแต่ละประเภทและแสดงจำนวนเหตุการณ์ที่เหลือก่อนถึงเกณฑ์; ไม่ต้องแสดงตัวนับและเกณฑ์ของทั้งสองประเภทตลอดเวลา

## ภาคผนวก F — มติ C-124 ที่ยืนยันเพิ่มเติม (ข้อ 1–24; 14 ต.ค. 2569)

**สถานะ:** CONFIRMED POLICY / PENDING DESIGN & TEST (GPS spoofing และการตรวจ Return Zone ด้วย GPS โทรศัพท์)

### F.1 ขอบเขตและการเก็บพิกัดโทรศัพท์ (มติ C-124)

- **[CONFIRMED]:** ใช้ GPS จากโทรศัพท์เป็นทางเลือกสำรองเฉพาะเพื่อยืนยัน Return Zone ตอนคืนรถ ไม่ใช้แทน GPS รถในการเริ่ม Session ใหม่; ความน่าเชื่อถือ GPS/การต้าน spoofing ต้องออกแบบและทดสอบก่อนใช้จริง
- **[CONFIRMED]:** เมื่อทำ Return Zone verification ด้วย GPS โทรศัพท์ ให้เก็บพิกัด latitude/longitude จริงทั้งกรณีตรวจผ่านและไม่ผ่าน สำหรับการตรวจสอบแต่ละครั้ง
- **[CONFIRMED]:** ลบอัตโนมัติเฉพาะพิกัดดิบของแต่ละครั้งเมื่อครบ 30 วันนับจากเวลาตรวจสอบครั้งนั้น ไม่ใช่ 30 วันหลังจบ Session; คงผลผ่าน/ไม่ผ่านและ timestamp ตามนโยบายเก็บ Session history ที่มีอยู่ โดยใช้ C-094 จัดการข้อมูลส่วนบุคคลเมื่อสิ้นสุดโครงการ
- **[CONFIRMED]:** Admin และ Manager สามารถตรวจดูพิกัดโทรศัพท์จริงที่ยังไม่ครบกำหนดลบย้อนหลังตามสิทธิ์บทบาท; เจ้าของข้อมูลเห็นพิกัดของตนเองในช่วงเก็บ 30 วันได้; ผู้ใช้อื่นห้ามดูพิกัดของผู้อื่น

### F.2 การสงสัย/ยืนยันการปลอมแปลง GPS

- **[CONFIRMED]:** เมื่อสงสัย GPS spoofing หรือการปรับแต่งตำแหน่ง ห้ามยืนยันคืนรถสำเร็จหรือเปลี่ยน Session เป็น Completed ให้คง Session เปิดอยู่ แจ้งทั้ง Admin และ Manager และต้องตรวจรถจริงก่อนพิจารณาปิด Session กรณีพิเศษ
- **[CONFIRMED]:** เมื่อมีเพียงข้อสงสัย ให้จำกัดสิทธิ์เริ่ม Session ใหม่ชั่วคราวระหว่างสอบสวน แต่ไม่เปลี่ยนบัญชีเป็น Suspended โดยอัตโนมัติ; ข้อจำกัดนี้เป็นคนละประเภทกับ Cancellation/No-show cooldown และ Safety Block
- **[CONFIRMED]:** เมื่อ Admin ยืนยันว่าผู้ใช้จงใจปลอมแปลง GPS เพื่ออ้างว่าคืนรถ ให้ Admin ระงับบัญชี (Suspended) ด้วยตนเอง ระบุเหตุผล และลง Audit Log; ไม่ให้ระบบระงับอัตโนมัติจากความสงสัย
- **[CONFIRMED]:** หาก Admin ตรวจสอบและยืนยันว่าไม่ได้ปลอมแปลง GPS ให้เฉพาะ Admin ปลดข้อจำกัดเริ่ม Session ใหม่ชั่วคราวด้วยตนเอง พร้อม Audit Log; การปลดนี้ไม่ได้ปิด Session เดิมหรือปลด Safety Block โดยอัตโนมัติ
- **[CONFIRMED]:** เว็บไซต์ต้องแจ้งผู้ใช้เมื่อพบความผิดปกติว่ากำลังตรวจสอบพิกัดและจำกัดสิทธิ์เริ่ม Session ใหม่ชั่วคราว พร้อมแสดงช่องทางติดต่อผู้ดูแล โดยไม่กล่าวหาว่าปลอมแปลงจริงก่อนมีผลสรุป; เมื่อสอบสวนเสร็จ ต้องแสดงผลและการดำเนินการต่อบัญชีแก่ผู้ใช้บนเว็บไซต์ ไม่เพิ่มช่องทางอีเมล

### F.3 คำอธิบายของผู้ใช้ผ่านโทรศัพท์

- **[CONFIRMED]:** ผู้ใช้ชี้แจงข้อสงสัยเกี่ยวกับ GPS ได้ผ่านหมายเลขโทรศัพท์กลางของโครงการที่แสดงบนเว็บไซต์เท่านั้น ไม่สร้างแบบฟอร์มชี้แจงใหม่เฉพาะเรื่องนี้
- **[CONFIRMED]:** Admin ต้องบันทึกสรุปคำชี้แจงของผู้ใช้เป็นข้อความ พร้อมวันเวลาและตัวตนผู้รับสาย โดยไม่บันทึกเสียงสนทนา
- **[CONFIRMED]:** Admin/Manager อ่านสรุปคำชี้แจงย้อนหลังได้ตามสิทธิ์ เจ้าของข้อมูลอ่านสรุปของตนเองได้แต่แก้ไขเองไม่ได้ ผู้ใช้ทั่วไปห้ามอ่านของผู้อื่น
- **[CONFIRMED]:** เก็บสรุปคำชี้แจงตลอดโครงการเป็นประวัติการสอบสวน; เมื่อสิ้นสุดโครงการให้จัดการข้อมูลส่วนบุคคลตาม C-094 ซึ่งแยกจากการลบพิกัด GPS ดิบ 30 วันหลังการตรวจสอบแต่ละครั้ง

### F.4 การแก้ไขสรุปคำชี้แจงและแจ้งเตือน

- **[CONFIRMED]:** เฉพาะ Admin แก้ไขข้อความสรุปคำชี้แจงได้ โดยต้องระบุเหตุผล และสร้าง Audit Log ที่เก็บข้อความก่อน/หลังแก้ ผู้แก้ และเวลาที่แก้
- **[CONFIRMED]:** ทุกครั้งที่ Admin แก้สรุป ให้สร้างการแจ้งเตือนเว็บไซต์แยกหนึ่งรายการต่อหนึ่งการแก้ ระบุวันเวลาและเหตุผล ไม่มีอีเมล แม้การแจ้งครั้งก่อนยังไม่ถูกรับทราบก็ต้องสร้างรายการใหม่
- **[CONFIRMED]:** แจ้งเตือนการแก้สรุปต้องคงอยู่ในรายการยังไม่รับทราบจนเจ้าของข้อมูลกด «รับทราบ» ของแต่ละรายการ และเก็บเวลารับทราบ; การกดรับทราบหมายถึงเห็นแจ้งเตือน ไม่ได้หมายถึงยอมรับเนื้อหาที่แก้
- **[CONFIRMED]:** การไม่กด «รับทราบ» ไม่ใช่เงื่อนไขห้ามเริ่ม Session ใหม่ หากผู้ใช้ผ่านเงื่อนไขการอนุญาตอื่นครบ; ไม่กระทบข้อจำกัด GPS spoofing, Suspended หรือ Safety Block ที่ยังมีผลอยู่
- **[CONFIRMED]:** หลังรับทราบแล้ว ให้เจ้าของบัญชีดูรายการแจ้งเตือนนั้นย้อนหลังได้อีก 30 วันนับจากเวลาที่กดรับทราบแต่ละรายการ ก่อนนำออกจากประวัติที่ผู้ใช้มองเห็นโดยอัตโนมัติ; คง Audit Log ตามนโยบายเดิม

### F.5 การขอแก้ไขสรุปและการไม่อนุมัติ

- **[CONFIRMED]:** ผู้ใช้ที่เห็นว่าสรุปคำชี้แจงของตนไม่ถูกต้องสามารถขอทบทวน/แก้ไขได้ผ่านหมายเลขโทรศัพท์กลางโครงการ โดย Admin เป็นผู้พิจารณาและเป็นผู้แก้ข้อความหากอนุมัติ; การแก้ต้องระบุเหตุผล มี Audit Log และแจ้งเว็บไซต์ตาม F.4 และไม่ตัดสิทธิ์ขอแก้ไขข้อมูลส่วนบุคคลตาม C-094
- **[CONFIRMED]:** ถ้า Admin ไม่อนุมัติคำขอแก้ไขสรุป ต้องบันทึกเหตุผลที่ปฏิเสธ ผู้ตัดสิน และวันเวลาตัดสิน คงสรุปเดิมไว้ และแจ้งผลการปฏิเสธแก่เจ้าของข้อมูลผ่านเว็บไซต์ โดยไม่เพิ่มการส่งอีเมล

## ภาคผนวก G — รายการยังเปิดอยู่ด้านออกแบบ/Pilot และข้อกำกับ

- C-123 [PENDING TEST]: ระยะเวลาที่รถออฟไลน์ก่อนสร้าง Dashboard Alert, เกณฑ์/ช่วงเวลาประเมินและระดับแจ้งเตือน Cancellation และ No-show, จำนวนครั้งที่นำไปสู่ข้อจำกัด และระยะเวลาคูลดาวน์ ต้องกำหนดจาก Pilot Test; ห้ามใส่ตัวเลขสมมติเป็นมติจริง
- C-123 [CONFIRMED Q61–Q69]: มติทั้งหมดถึง Q69 ยืนยันแล้ว; ดูภาคผนวก E; ค่าเกณฑ์ตัวเลขและเวลาจริงรอ Pilot
- C-124 [PENDING DESIGN/TEST]: วิธีตรวจ spoofing/การบิดเบือนตำแหน่ง ความไว/ความน่าเชื่อถือ GPS โทรศัพท์ และเงื่อนไขการตรวจรถจริงต้องออกแบบและทดสอบ; การยืนยันนโยบายไม่ถือเป็นผลทดสอบผ่าน
- C-094 [APPLICABLE]: เมื่อสิ้นสุดโครงการต้องลบหรือทำข้อมูลส่วนบุคคลไม่ให้เชื่อมกลับได้ภายใน 30 วันตามข้อกำหนดเดิม โดยเคารพหน้าที่และข้อยกเว้นตามกฎหมาย
- ขอบเขตฉบับปรับปรุงครอบคลุมมติ C-123/Q69, C-124 และ C-128–C-144; ยังมีงานออกแบบ/ตัวเลข Pilot/การพิสูจน์ความปลอดภัย และไม่ถือว่าพัฒนาหรือทดสอบผ่านแล้ว



## ภาคผนวก H — ข้อกำหนดเพิ่มเติมที่ยืนยันถึง C-144 (14 ต.ค. 2569)

> **ลำดับความสำคัญของมติ:** มติฉบับแก้ล่าสุดมีผลแทนข้อความเดิมเฉพาะจุดขัดแย้ง โดยเฉพาะ C-003/C-019/C-025–C-028 และระบบที่เคยใช้กุญแจจริง; ไม่มีข้อกำหนดให้ใช้กุญแจรถจริงอีกต่อไป คำว่า Motor Ready เป็นสถานะอนุญาต ไม่ใช่การสั่งรถเคลื่อนที่เอง

### H.1 C-123/Q61–Q69 — Cancellation / No-show

- **C-123/Q61 [CONFIRMED; B]:** เมื่อ No-show cooldown หมดอายุเองขณะที่มีรายการรออนุมัติปลดข้อจำกัดจากการชดเชยข้ามรอบ ให้ปิดรายการรออนุมัตินั้นโดยอัตโนมัติ ปรับสถานะบนเว็บไซต์ตามจริง โดยไม่สร้างแจ้งเตือนใหม่
- **C-123/Q62 [CONFIRMED; A]:** กรณี Admin/Manager อนุมัติปลดข้อจำกัด No-show ก่อนเวลาหมดอายุ ให้แจ้งผู้ใช้ผ่านเว็บไซต์ทันที ระบุเหตุผลและวันเวลาปลด ไม่ต้องกดรับทราบ
- **C-123/Q63 [CONFIRMED; A]:** เก็บแจ้งเตือนปลดข้อจำกัดก่อนกำหนดตาม Q62 ในประวัติที่ผู้ใช้มองเห็น 30 วันนับจากเวลาสร้าง แล้วนำออกอัตโนมัติ โดยคง Audit Log ตามนโยบายเดิม
- **C-123/Q64 [CONFIRMED; B]:** หลัง Admin/Manager อนุมัติปลดข้อจำกัด No-show ก่อนกำหนด ให้รีเซ็ตตัวนับ No-show เป็น 0 และเริ่มรอบประเมิน No-show ใหม่ทันที
- **C-123/Q65 [CONFIRMED; A]:** การรีเซ็ตเมื่อปลด No-show ก่อนกำหนดตาม Q64 กระทบเฉพาะตัวนับ No-show; ตัวนับ Cancellation และรอบประเมินของ Cancellation ยังคงเดิม
- **C-123/Q66 [CONFIRMED; A]:** เมื่อ Cooldown ของ Cancellation หรือ No-show สิ้นสุด ให้รีเซ็ตเฉพาะตัวนับของประเภทที่สิ้นสุดและเริ่มรอบประเมินใหม่ของประเภทนั้น; ไม่กระทบข้อจำกัดอีกประเภท
- **C-123/Q67 [CONFIRMED; A]:** Admin สามารถปรับเกณฑ์จำนวนครั้งที่ก่อให้เกิดข้อจำกัด Cancellation/No-show และระยะเวลา Cooldown ผ่านเว็บไซต์ได้; ค่าตั้งต้นเชิงตัวเลขยังต้องมาจาก Pilot Test
- **C-123/Q68 [CONFIRMED; A]:** เกณฑ์และระยะเวลา Cooldown ใหม่ที่ Admin เปลี่ยนให้ใช้เฉพาะการประเมินหลังเวลาที่เปลี่ยน ไม่ย้อนหลังและไม่เปลี่ยนข้อจำกัดที่เริ่มก่อนหน้านั้น
- **C-123/Q69 [CONFIRMED; B]:** Dashboard แสดงเฉพาะคำเตือนเมื่อ Cancellation หรือ No-show ใกล้ถึงเกณฑ์ แยกแต่ละประเภทและแสดงจำนวนเหตุการณ์ที่เหลือก่อนถึงเกณฑ์; ไม่ต้องแสดงตัวนับและเกณฑ์ของทั้งสองประเภทตลอดเวลา

### H.2 C-128–C-144 — การใช้รถไร้กุญแจ การจอดพัก และการคืนรถ

- **C-128 [CONFIRMED; B]:** หลัง Pilot Test ผ่านเกณฑ์ความปลอดภัย ให้ Student, Employee, Manager ที่ได้รับอนุมัติใช้งานในพื้นที่/เงื่อนไขมหาวิทยาลัยอนุญาตได้; Admin ไม่ใช่ผู้ขับ; ไม่มีสิทธิ์ใช้ถนนสาธารณะโดยอัตโนมัติ
- **C-129 [CONFIRMED; A]:** ผู้ขับต้องตรวจสภาพรถเบื้องต้นด้วยตนเอง เช่น เบรก/ยาง และยืนยันผ่าน Responsive Web App ก่อน Session Start ทุกครั้ง; ไม่ทดแทน Safety Block หรือการตรวจระบบ
- **C-130 [CONFIRMED; A]:** บันทึกตัวตนผู้ขับและเวลาในการยืนยันตรวจสภาพรถก่อนทุก Session; Admin/Manager ตรวจย้อนหลังได้ตามสิทธิ์; อายุการเก็บให้เป็นไปตามนโยบายประวัติที่ใช้อยู่จนกว่าจะกำหนดเพิ่ม
- **C-131 [CONFIRMED; A]:** ทีมงานต้องแนะนำวิธีใช้งานและความปลอดภัยแก่ผู้ขับก่อนการใช้งานครั้งแรก; ไม่จำเป็นต้องสร้างหลักสูตรออนไลน์
- **C-132 [CONFIRMED; B; REVISED BY C-136]:** ทีมงานตรวจว่าผ่านการแนะนำนอกเว็บไซต์ ไม่ต้องสร้างระบบการอบรมออนไลน์ แต่ระบบต้องมี Driving Permission แยกจาก Approved ให้ Admin เปิดหลังทีมงานยืนยันผ่านตาม C-136
- **C-133 [CONFIRMED; B; REVISED BY C-136]:** Admin อนุมัติบัญชีตามปกติโดยไม่ต้องรอการแนะนำ ทีมงานกำกับการใช้งานครั้งแรก แต่ผู้ใช้จะเริ่มรถจริงไม่ได้จน Admin เปิด Driving Permission
- **C-134 [CONFIRMED; REVOKED]:** ยกเลิกมติเดิมเรื่องทีมงานเก็บ/ส่งมอบกุญแจรถจริง เพราะโครงการไม่ใช้กุญแจจริง
- **C-135 [CONFIRMED; REVOKED]:** ยกเลิกมติเดิมเรื่องผู้ผ่านการแนะนำเข้าถึงหรือเก็บกุญแจรถจริง เพราะโครงการไม่ใช้กุญแจจริง
- **C-136 [CONFIRMED; A; REVISED]:** ก่อนเริ่มผ่าน NFC หรือเว็บต้องผ่านการแนะนำจากทีมงาน แล้ว Admin เปิด Driving Permission แยกจาก Account Approved; ทุกช่องทางตรวจสิทธิ์เริ่มรถบนเซิร์ฟเวอร์ก่อน Session Start; มติ C-136 เดิมเรื่องคืนกุญแจถูกยกเลิก
- **C-137 [CONFIRMED; A]:** ใช้ Responsive Web App ผ่านเบราว์เซอร์มือถือ/คอมพิวเตอร์เท่านั้น ไม่พัฒนา native Mobile App แยก
- **C-138 [CONFIRMED; B]:** เมื่อ NFC/เว็บตรวจสิทธิ์และเงื่อนไขครบ ไม่ต้องกดยืนยันที่ตัวรถหรือเปลี่ยน OFF→ON อีกขั้นก่อน Motor Ready; ต้องพิสูจน์วงจรไร้กุญแจและความปลอดภัยจริง; Motor Ready ไม่ใช่การทำให้รถเคลื่อนเอง
- **C-139 [CONFIRMED; A]:** ต้องตรวจว่าผู้ใช้อยู่ใกล้ตัวรถจริงก่อนอนุญาต Motor Ready โดยไม่ต้องกดยืนยันเพิ่ม; หากยืนยันไม่ได้ห้าม Motor Ready; วิธีตรวจต้องออกแบบ/ทดสอบและไม่สันนิษฐานว่า GPS มือถืออย่างเดียวเพียงพอ
- **C-140 [CONFIRMED; B]:** เมื่อเริ่ม Active Session และ Motor Ready แล้ว การเดินออกห่างรถเพียงอย่างเดียวไม่ทำให้ยกเลิก Motor Ready; คงตามสถานะ Session จนสิ้นสุดหรือมีคำสั่ง Pause/Lock ที่ปลอดภัยตาม C-142; ต้องบันทึกความเสี่ยงผู้ที่ไม่ได้รับอนุญาตใช้รถที่จอดทิ้งไว้
- **C-141 [CONFIRMED; A]:** เจ้าของ Session สั่งจบผ่าน NFC หรือ Responsive Web App ระบบต้องตรวจหยุดนิ่งและ Return Zone ตามข้อยกเว้นที่อนุญาต ก่อน Completed; ไม่ต้องใช้กุญแจ OFF
- **C-142 [CONFIRMED; A; NFC INCLUDED]:** เพิ่ม Pause/Lock เมื่อยืนยันว่ารถหยุดนิ่ง ผู้ใช้สั่งพักได้ผ่าน NFC หรือเว็บ; ขณะ Pause มอเตอร์ไม่พร้อมขับ แต่ยังคง Session เดิม ผู้ขับเดิม Resume ผ่าน NFC/เว็บได้หลังตรวจสิทธิ์ออนไลน์ ความใกล้รถ และความปลอดภัยใหม่; ห้ามล็อก/ตัดกำลังขณะกำลังขับ; การเดินออกห่างเฉย ๆ ไม่ถือว่าสั่ง Pause
- **C-143 [CONFIRMED; A]:** End Session แบบปกติต้องมีผลยืนยันว่า Motor Ready ปิดจริง ไม่ใช่เพียงรับ ACK ก่อน Completed; ถ้าตรวจผลปิดไม่ได้ คง Pending End และห้ามคนอื่นเริ่มรถจนตรวจสอบและแก้ไขอย่างปลอดภัย
- **C-144 [CONFIRMED; A]:** หากคืนรถไม่สำเร็จ เว็บไซต์ต้องแสดงสาเหตุจริงที่ตรวจพบและคำแนะนำดำเนินการต่อ เช่น กลับ Return Zone รอการตรวจหยุดนิ่ง หรือติดต่อเจ้าหน้าที่; ห้ามกล่าวอ้างว่า Completed เมื่อยังตรวจไม่ผ่าน

### H.3 กติกาสรุปการเดินสถานะ (ชี้ขาดความขัดแย้งเดิม)

- **เริ่มใช้:** Account Approved ไม่เท่ากับ Driving Permission. ก่อนทุก Session ต้องมี Driving Permission ที่ Admin เปิดหลังทีมงานยืนยันการแนะนำ (C-136); ผู้ขับตรวจสภาพเบื้องต้น เช่น เบรก/ยาง และยืนยันผ่าน Responsive Web App แม้ขอเริ่มผ่าน NFC พร้อมบันทึกตัวตนและเวลาการยืนยัน (C-129/C-130). หากไม่มีสิทธิ์ขับหรือหลักฐานยืนยันตรวจสภาพของรอบนั้น ห้าม Session Start. อนุมัติออนไลน์, Reservation แบบ Atomic, ตรวจคันเร่งศูนย์/รถนิ่ง/BMS/AI/GPS ตามบทบาท และยืนยันว่าผู้ขับอยู่ใกล้รถก่อน Motor Ready. ทั้ง Web และ NFC ใช้การตรวจสิทธิ์เดียวกัน; ไม่ต้อง OFF→ON หรือกดที่รถเพิ่ม.
- **ใช้งานปกติ:** Active Session ให้ผู้ขับเจ้าของสิทธิ์คนเดียว; การออกห่างโดยลำพังไม่หยุด Motor Ready (C-140) และมีความเสี่ยงด้านการถูกใช้โดยผู้อื่น. ต้องประเมินความเสี่ยงนี้ก่อน Pilot.
- **Pause/Lock:** เมื่อจอดนิ่งและผู้ขับสั่ง Pause ผ่าน NFC/เว็บจึงเปลี่ยนเป็นล็อกชั่วคราว, ไม่อนุญาต Motor Ready, Session ยังเปิดอยู่; Resume โดยเจ้าของเดิมผ่านเว็บ/NFC ภายใต้การตรวจสิทธิ์ออนไลน์ ความใกล้ และความปลอดภัยครั้งใหม่. ห้ามใช้คำสั่งล็อกตัดกำลังรถที่กำลังวิ่ง.
- **End:** เจ้าของสั่ง End ทางเว็บ/NFC; ตรวจรถหยุดนิ่ง Return Zone (หรือข้อยกเว้นเดิมที่ตรวจสอบได้) และยืนยัน Motor Ready ปิดจริง ก่อน Completed. ไม่เกิด Completed เพราะรถจอดนิ่งอย่างเดียว; ถ้าตรวจไม่ได้คง Pending End และกันผู้ใช้อื่นเริ่ม.
- **คืนรถไม่สำเร็จ:** เว็บไซต์แจ้งสาเหตุที่ตรวจพบและคำแนะนำเพื่อแก้ไข; GPS โทรศัพท์ fallback เฉพาะตรวจคืนรถตาม C-124 และกฎตรวจ spoofing เดิม; การปิดกรณีพิเศษต้องตรวจรถจริงและทำบันทึกตาม C-030.
- **พร้อมใช้ใหม่:** หลัง Completed และผ่านเงื่อนไขความปลอดภัยทั้งหมดจึง Available ตาม C-031; การปิด Motor Ready/การสื่อสาร/การตรวจความใกล้ต้องทดสอบกับฮาร์ดแวร์จริง.

### H.4 สถานะงานออกแบบและทดสอบที่ไม่ใช่มติยืนยันความสำเร็จ

- **PENDING DESIGN/TEST:** ตรวจวงจร VOTOL EM100/E-lock/Enable แบบไร้กุญแจ, อุปกรณ์ยืนยัน Motor Ready ปิดจริง, interlock ป้องกันเริ่มผิดจังหวะ, การปลอดภัยหากอุปกรณ์หรือการสื่อสารเสีย, วิธีตรวจผู้ใช้อยู่ใกล้รถที่ต้านการปลอมตำแหน่ง/relay, UX คำสั่ง NFC แยก Pause/Resume/End โดยไม่กำกวม, และห้ามตัดกำลังระหว่างเคลื่อนที่.
- **PENDING PILOT:** ตัวเลขเกณฑ์ Cancellation/No-show, near-warning thresholds, evaluation windows, Cooldown, offline alert period, และเกณฑ์ AI/GPS/การใช้งานที่ต้องทดลองจริง; Admin เปลี่ยนเกณฑ์ภายหลังได้ตาม C-123/Q67–Q68 เท่านั้น.
- **PENDING DOC IMPLEMENTATION:** มติในเอกสารนี้เป็น policy/design baseline ยังไม่ใช่หลักฐานว่าพัฒนา/ติดตั้ง/ทดสอบ/ได้รับอนุญาตใช้บนถนนสาธารณะจริง; C-094 privacy และ C-124 ลบพิกัดโทรศัพท์ดิบตามกำหนดยังคงใช้.


บันทึกการแก้ไขข้อกำหนด 15 ตุลาคม 2569 — สิทธิ์ Student/Employee (REV-2026-10-15-01)

มติใหม่ของเจ้าของโครงการ: Student (นักศึกษา) และ Employee (บุคลากร) มีสิทธิ์การใช้งานและข้อจำกัดเหมือนกันทุกประการ โดยยึดข้อกำหนดของ Student เป็นหลัก ต่างกันเฉพาะชื่อ/ประเภทบทบาท
- ทั้งสองบทบาทต้องผ่านเงื่อนไขความพร้อมของ AI, วัน/เวลาเริ่ม, Main Geofence, Return Zone, GPS, เงื่อนไขอนุญาตขับและความปลอดภัยเดียวกัน
- เมื่อ AI ไม่พร้อมหรือ Polygon ยังไม่มี/รถอยู่นอก Geofence/Return Zone ไม่พร้อม ให้ใช้ข้อห้ามเริ่มรอบของ Student กับ Employee เท่าเทียมกัน; การออกนอกเขตระหว่างขับใช้กติกาแจ้งเตือนเดียวกันโดยไม่ตัดกำลังขณะเคลื่อนที่
- ยกเลิกข้อยกเว้นของ Employee ในข้อความเดิม C-005, C-028, C-110, C-115 และ D-003 เฉพาะส่วน Employee; ข้อกำหนด Manager/Admin ไม่เปลี่ยน
- การอนุมัติบัญชีไม่เท่ากับการมี Driving Permission; ทั้งสองบทบาทต้องได้รับสิทธิ์ขับแยกและยืนยันตรวจสภาพรถก่อนเริ่มตามมติที่มีอยู่แล้ว
- การแก้ไขครั้งนี้เป็นการเปลี่ยนมติด้านบทบาท ไม่ใช่หลักฐานว่าระบบพัฒนา/ผ่านการทดสอบแล้ว; ในการบันทึก REV-2026-10-15-01 ชื่อยังรอเลือก แต่ภายหลังเจ้าของโครงการยืนยันชื่อไทยว่า “ระบบรถจักรยานยนต์ไฟฟ้าสาธารณะพร้อมระบบ AI ช่วยเตือนการขับขี่” และอัปเดตครบแล้ว (FIX-09) โดยภายหลังได้ปรับชื่อภาษาอังกฤษเป็น “Public Electric Motorcycle System with AI-Assisted Riding Alerts” ให้ตรงกับชื่อไทย
